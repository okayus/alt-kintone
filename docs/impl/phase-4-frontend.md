# フェーズ4: FE + 動作確認

ハブ: [../implementation.md](../implementation.md)

**目的**: ブラウザで営業フローを操作できるようにする。ここまで来れば構想の検証ができる。

> **着手時に詳細化すること。** いまは概要と完了条件だけ。

---

## タスク概要

### 4-1. 共通シェル

ナビゲーション・レイアウト・APIクライアント。**1つのアプリに統合する**
（業務フローごとに別アプリにしない。`product-concept.md` §4-3）。

共通化するのはシェルだけ。一覧やフォームを共通部品に寄せない
（部品の表現力が上限になるのが kintone の失敗構造）。

### 4-2. 業務フローの画面

`apps/main/src/flows/sales/` に置く。最小スコープでは案件の一覧と詳細だけ。

**業務フロー定義が UI に現れること**が最重要。ここが構想の核がユーザーに届くかの分かれ目。

```
【案件】山田食堂 / 求人広告

●──●──○──○
接触  ヒアリング  提案  受注
     ↑いまここ

次に進むための確認
  ☑ 予算感を確認した          ← 自動判定
  ☐ 決裁者に会えている         ← 自動判定（未充足）
  ☐ 顧客が課題を語れている      ← 手動チェック

  [提案へ進める]  ※未確認2件あり
```

- **ウィザードにしない。** 営業の進行は非線形（`sales-domain.md` §4-7）
- 未充足でも進めるボタンは押せる。警告を出すだけ
- 編集可否は API が返す `_permissions` を見る。**FE で再判定しない**

### 4-3. ポート公開と動作確認

`docker-compose.yml` のポートはいま**外してある**。ホストの 3000 / 5173 は別プロジェクトの
コンテナが使用中なので、**空きポートを確認してから**追加する。

```sh
ss -ltn | grep -E ':(3000|3100|5173|5273)'   # 空きを確認
docker ps --format '{{.Names}}\t{{.Ports}}'
```

匿名ボリュームの追記も忘れないこと（パッケージを増やしたとき）。

---

## 完了条件

ブラウザで以下ができる。

1. 案件一覧が見える（現在ステップつき）
2. 案件詳細で、現在地と出口条件のチェックリストが見える
3. 自動判定の出口条件が、データを直すと勝手に充足に変わる
4. 手動チェックを付け外しできる
5. ステップを進められる。未充足でも進めるが記録が残る
6. 担当者でない案件は編集ボタンが出ない

3 が確認できれば、**「営業の入力負担を減らす」という構想の中核が実際に働いている**ことになる。
