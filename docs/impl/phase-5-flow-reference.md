# フェーズ5: 業務フローの参照画面

ハブ: [../implementation.md](../implementation.md)

**目的**: 営業が**レコードを経由せずに業務フローそのものを読める**ようにする。
異動してきた人が「この会社の営業はどう進むのか」を画面だけで把握できる状態にする。

---

## 0. 全体像

フェーズ4までで、業務フローは**レコード経由でしか見えない**。案件を開くと
「自分がいまいる1ステップ分」の出口条件だけが出る。全体像・他のステップの条件・
遷移の可能性・各段階の意図は、定義ファイルを読める人にしか見えない。

```
いま                                これから
┌─────────────────┐               ┌─────────────────┐
│ 案件詳細        │               │ 案件詳細        │
│  現在地（1点）  │               │  現在地（1点）  │
│  出口条件       │               │  出口条件       │
│   ラベルだけ    │               │   + 充足のしかた │ ← 5-2
│                 │               │  [フロー全体を見る]│
└─────────────────┘               └────────┬────────┘
                                            ↓
                                  ┌─────────────────┐
                                  │ 業務フロー参照   │ ← 5-3（新規）
                                  │  ゴール          │
                                  │  遷移グラフ      │
                                  │  ステップのカード │
                                  │   意図/担当/条件 │
                                  │  使うデータ      │
                                  └─────────────────┘
```

**必要な情報のほとんどは既に定義にある**（ステップ名・出口条件のラベル・担当ロール・
`bindings.purpose`・`flow.goal`）。画面に出していないだけ。フェーズ4で
**定義を値として import する**と決めた（決定B）ので、この画面は**API を1本も叩かない**。

足りないのは2つで、**どちらも定義側に足す**。

| 足りないもの | 現状 | 対応 |
|---|---|---|
| **テーブル/フィールド/enum の表示名** | `FieldDef` は `type` / `required` / `references` / `values` だけ | 定義に持たせる（**§8-2 論点14 を解く**） |
| **出口条件をどうすれば満たせるか** | AST はあるが人が読めない | 説明文を定義に持たせる + **AST から参照フィールドを機械抽出** |
| **なぜこの段階があるのか** | 書く場所が無い | `step({ intent })` を足す |

## 決めたこと（詳細化で決めた設計判断）

| # | 決定 | 理由 |
|---|---|---|
| A | **表示名は定義に持たせる**。`text('案件名')` / `table('deal', {...}, { label: '案件' })` / `enumOf('商材', [{key,label}])` の形で、**ラベルは必須**（型で強制） | 論点14 の解決。一度やれば出口条件の AST を日本語で読ませられ、`DealForm.tsx` と `labels.ts` の手書きも消える。省略可にすると必ず書かれないものが出て、画面に英語キーが漏れる |
| B | **enum は `readonly string[]` から `ReadonlyArray<{key,label}>` へ**。`valueLabels` を別に持つ形は採らない | 二重管理を作らない。配列にするのは**順序を保つ**ため（`Record` にすると Go の map 反復順が不定になり表示順が失われる）。読んでいるのは3箇所だけなので変更コストは小さい |
| C | **出口条件に `howTo`（充足のしかた）を必須で持たせる** | オンボーディングの主payload。「なぜ ☐ なのか」が画面で分かる。手動チェックにも持たせる（「どういう状態なら ✓ にしてよいか」） |
| D | **`howTo` と並べて「この条件が見ているデータ」を AST から機械抽出して出す** | `howTo` は手書きなので条件を変えて直し忘れるとズレる（`label` と同じリスク）。機械抽出の一覧を**併記**すれば、ズレが目視で分かる。検査で防げないものを表示で見えるようにする |
| E | **`step({ intent })` を必須で持たせる** | `sales-domain.md` の「ステージは**買い手の状態変化**で定義する」という原則が、定義そのものに残る。kintone には原理的に持てない情報 |
| F | **遷移はグラフで描く。レイアウトは自前**（ライブラリを入れない） | 描くのは7ノード。前進/後退/スキップの描き分けと現在地の強調が要るので、汎用ライブラリだと結局書き換えることになる。アルゴリズムは 5-3 に書いた |
| G | **グラフは骨格、詳細はカード**。ノードを選ぶと関係する辺だけ強調し、カードへスクロールする | 分岐・差し戻し・スキップがあるので線は必ず混む。**混んでも読める**ようにするのは、全部を線で見せることではなく、見る範囲を絞れること |
| H | **画面はエンドユーザーFE に置く**（管理画面FEではない） | 対象が営業。§4-3 の「横断ビューは既存バインディングの再利用に限る」に沿う — というより**データを1件も読まない**（定義だけ）ので、新しいテーブルアクセスが発生しない |
| I | **「何が変わったか」は作らない**（今回は参照画面だけ） | 定義の版を積む仕組み（プラットフォームテーブル + `alt apply` の変更 + 差分の言語化）が要り、§8-2 論点5（`alt diff`）と重なる。オンボーディングは参照画面だけで満たせる |

## 5-0. `@alt/dsl` の拡張

**ここが全パッケージに波及する。先に済ませる。**

### `table.ts`

```ts
export interface EnumValue {
  key: string      // DB に入る値。条件式 AST のリテラルになる
  label: string    // 表示だけ
}

export interface FieldDef {
  type: FieldType
  label: string            // ← 追加（必須）
  required: boolean
  primaryKey: boolean
  references?: string
  values?: readonly EnumValue[]   // ← readonly string[] から変更
}

export interface TableDef {
  name: string
  label: string            // ← 追加（必須）
  global: boolean
  fields: Record<string, FieldDef>
}
```

ビルダーは**ラベルを第1引数**に取る。

```ts
export const text = (label: string) => builder({ type: 'text', label, … })
export function enumOf(label: string, values: readonly EnumValue[]): FieldBuilder
export function reference(tableName: string, label: string): FieldBuilder
export function table(name, fields, opts: { label: string; global?: boolean }): TableDef
```

### `flow.ts`

```ts
export interface AutoCheck {
  kind: 'auto'; key: string; label: string
  howTo: string        // ← 追加（必須）。どうすれば充足するか
  condition: Pred
}
export interface ManualCheck {
  kind: 'manual'; key: string; label: string
  howTo: string        // ← 追加（必須）。どういう状態なら ✓ にしてよいか
}
export interface StepDef {
  key: string; name: string
  intent: string       // ← 追加（必須）。この段階で何を目指すのか
  role: string; reads: string[]; writes: string[]
  exit: ExitCondition[]; next: string[]
}
```

呼び出しは既存の流儀（位置引数）に合わせる: `check(key, label, howTo, condition)` /
`manualCheck(key, label, howTo)`。`step` は既にオブジェクト形なので `intent` を足すだけ。

### `ast.ts` — 参照フィールドの抽出（決定D）

```ts
export interface FieldRef {
  /** 述語のどのテーブルか。ROOT_SOURCE ならフローの target。 */
  source: string
  path: readonly string[]
}
/** 述語が参照しているフィールドを重複なく列挙する（表示用）。 */
export function referencedFields(pred: Pred): FieldRef[]
```

`exists` の入れ子も辿る。**表示のためだけの道具**で、TS と Go の契約（AST そのもの）
ではない — Go 版に移す必要は無い、とコメントに明記する。

### zod スキーマと波及先

`fieldDefSchema` / `tableDefSchema` / `exitConditionSchema` / `stepDefSchema` を更新する。
**古い `data/definitions.json` は読めなくなる**ので `alt export --out` を流し直す
（サーバのロジック変更は無い）。

`field.values` を読んでいるのは3箇所だけ。

| 場所 | 変更 |
|---|---|
| `packages/dsl/src/table.ts` | zod の `refine`（enum に values があること） |
| `packages/server/src/record-input.ts` | `values.includes(v)` → `values.some(x => x.key === v)`。候補の表示も |
| `apps/main/src/flows/sales/DealForm.tsx` | `values.map` が `{key,label}` を受ける（**`labels.ts` を引かなくなる**） |

## 5-1. 定義に表示情報を入れる

`@alt/definitions` の**57フィールド・5テーブル・12 enum・7ステップ・8出口条件**に
ラベル / `howTo` / `intent` を入れる。機械的だが件数はある。

ラベルの出どころは `docs/domain-model.md` §5（表示ラベルで書かれた属性表）と §5-0（enum 対応表）。
**すでにドキュメントにある文言を定義へ移すだけ**で、新しく考える必要はない。

```ts
export const deal = table(
  'deal',
  {
    id: uuid('ID').primaryKey(),
    companyId: reference('company', '顧客企業').required(),
    title: text('案件名').required(),
    productType: enumOf('商材', [
      { key: 'job_ad', label: '求人広告' },
      { key: 'meo', label: 'MEO' },
      { key: 'other', label: 'その他' },
    ]).required(),
    initialBilling: integer('一時金・請求額'),
    …
  },
  { label: '案件' },
)
```

`employee.role` の enum は**ロール宣言から生成する**（`roles.map(r => ({ key: r.key, label: r.name }))`）。
ロールを足したときにラベルを書き足し忘れることが構造的に起きない。

出口条件と意図（`docs/sales-domain.md` の語彙で書く）:

```ts
step({
  key: 'qualified',
  name: 'ヒアリング',
  intent: '買い手が自分の課題を言語化できている状態にする。売り手が資料を作ったかではなく、買い手の状態で判定する',
  role: 'sales_rep',
  exit: [
    manualCheck('problem_identified', '課題を確認した',
      '先方が自分の言葉で困っていることを説明できたら ✓。こちらが推測した課題では立てない'),
    check('budget_confirmed', '予算感を確認した',
      '案件の「一時金・請求額」か「月額・請求額」のどちらかに金額を入れると充足する',
      amountEntered),
    …
  ],
  …
})
```

## 5-2. 既存FEの整理と、案件詳細への `howTo`

**手書きが消える**（論点14 が解決する）。

| ファイル | 変更 |
|---|---|
| `flows/sales/labels.ts` | **enum ラベルの表を全部削除**。定義から引く `label(field, value)` に置き換え。`roleLabel` は残る（元から定義由来） |
| `flows/sales/DealForm.tsx` | フィールドのラベル（`'案件名'` など）を定義から取る。`Field label=` の手書きが消える |
| `flows/sales/DealList.tsx` / `DealDetail.tsx` | 列見出し・項目名を定義のラベルから |

**案件詳細のチェックリストに `howTo` を出す。** 未充足の自動判定にこそ要る。

```
次に進むための確認
  ☑ 課題を確認した          手動
  ☐ 予算感を確認した        自動判定
      → 案件の「一時金・請求額」か「月額・請求額」に金額を入れると充足する
  ☑ 決裁者を特定した        自動判定
```

充足済みのものは畳む（未充足だけ開く）。日常の使用でノイズにしないため。

## 5-3. フロー参照画面（`apps/main/src/flows/` と シェル）

ルートは `#/flows/:key`、ナビに「業務フロー」を足す。**フローが増えても壊れない形**にする
（`flows` 配列を回す）。画面とレイアウトは**フロー非依存**なので `flows/sales/` ではなく
`flows/` 直下に置く（実装時に確定。`FlowReference.tsx` / `flowGraph.ts`）。

### 画面の構成

```

┌─ 遷移 ────────────────────────────────────────────────┐
│                    ┌──────────────┐                    │
│                    ↓（差し戻し）   │                    │
│   接触 ──→ ヒアリング ──→ 提案 ──→ 受注                │
│    │  └────────────────↗  │ │                          │
│    │      （即決）        │ ├──→ 失注                  │
│    │                      │ └──→ 消滅                  │
│    └──→ ヒアリング…       ↓                            │
│              └──→ 保留 ──┘（再開）                     │
│                                                        │

（ステップのぶんだけカードが続く）

┌─ この業務で使うデータ ─────────────────────────────────┐
```

「使うデータ」は `bindings` の `role` / `purpose` と、`usedTables()` が導出する
access をそのまま出す。**バインディングという概念が営業にも見える形**になる。

### グラフのレイアウト（決定F）

純関数にしてテストする（`flowGraph.ts`）。

1. **後退辺の検出** — `initial` から DFS し、訪問中のノードへ戻る辺を後退辺とする
   （営業フローでは `提案→ヒアリング`、`保留→ヒアリング`）
2. **層（rank）の割当** — 後退辺を除いた DAG に**最長経路法**を使う。
   `rank(v) = max(rank(u) + 1)`（u は前任者）。最短経路にすると、`接触→提案`（即決）で
   提案が ヒアリング と同じ層に来て、順序が壊れる
   - 営業フロー: `接触0 / ヒアリング1 / 提案2・保留2 / 受注3・失注3・消滅3`
   - 決着（`next` が空）が自然に最終層へ集まる
3. **層内の並び** — 定義の宣言順
4. **辺の種類** — 前進（rank +1）／スキップ（rank +2以上）／後退。線種で描き分ける
5. **描画** — SVG。層を左→右、層内を縦。スキップ辺はノードの上、後退辺は下を回す

**ノードを選ぶと、その入出辺だけを濃くし他を薄くする**（決定G）。線が混むのは
避けられないので、全部を同時に読ませない。選択はカードへのスクロールも兼ねる。

> ⚠ ステップが増えるとレイアウトは必ず苦しくなる。**苦しくなったらグラフを捨てて
> カードだけにできる**ようにしておく（カードは定義から直接出るので、グラフに依存しない）。

2. 段階はいくつあり、それぞれ何を目指すのか

## 完了条件

1. ナビから業務フローの参照画面へ行ける。**フロー名・ゴール・ステップが定義から出る**
2. 遷移グラフが描かれ、**前進 / 差し戻し / スキップが区別できる**。ノードを選ぶと関係する辺が強調される
3. 各ステップのカードに、**意図・担当ロール・出口条件（自動/手動）・充足のしかた・出入りするステップ**が出る
4. 自動判定の出口条件に「**この条件が見ているデータ**」が AST から機械抽出されて出る
5. 案件詳細の**未充足の自動判定に、充足のしかたが出る**
6. `labels.ts` の enum ラベル表と `DealForm` のフィールドラベルの**手書きが消えている**（定義から来る）
7. 定義に**ラベル / `howTo` / `intent` を書き忘れると型エラーになる**
8. `docker compose exec dev pnpm verify` が通る

3 と 4 が揃えば、**異動者が定義ファイルを読まずに業務を把握できる**ことになる。

## ここまで来たら

- **§8-2 論点14 は解決**する（enum ラベル・フィールドラベルが定義に入る）。§8-2 から落とす
- 残る近い論点は **論点15**（`table()` の型消去。`RecordOf<typeof deal>` の導出）。
  ラベルを足すためにビルダーを触るので、**同時にやると安い可能性がある** — 5-0 に着手した
  時点で判断する → **見送った**。ラベルは値レベル・型導出は型レベルで直交し、
  ジェネリクスは後から足しても手戻りが無い（`product-concept.md` §8-1 フェーズ5）
- 「業務の変更」（定義の版と差分）は次の候補
