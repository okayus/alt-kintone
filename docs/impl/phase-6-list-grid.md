## 2. 前提の解説

論点の手前に、判断に使う概念を並べる。

### 2-1. 「1万件の一覧」は独立した2つの仕組みでできている

- **描画の仮想化**（DOM）: 画面に見えている行+前後だけを DOM に置き、スクロールに合わせて
  差し替える。全体の高さはダミーの余白で確保する。1万件でも DOM 上は常に数十行
- **取得のウィンドウ化**（通信）: 表示に必要な範囲+バッファだけをサーバから引く

前者が無いと「全件持っていても描画が重い」、後者が無いと「初回ロードと転送が重い」。
独立した仕組みなので片方だけの構成もあり得る（1万件を一括で持ち描画だけ仮想化する、など。
社内・低トラフィックなら成立しなくはない）。ただし要求は取得も絞ると言っているので両方やる。
両者は「いま何行目が見えているか」でだけ結合する。

### 2-2. スクロール取得の3方式と「行ズレ」— 有効期間型の配当

窓取得には定番の問題がある。**取得の合間にデータが変わると行がズレる**。
offset 方式で200件目まで見たあとに誰かが1件更新すると、並び（更新順・金額順…）の中で
行が動き、次の窓で**同じ行が二度出る／一度も出ない**が起きる。

| 方式 | 仕組み | 難点 |
|---|---|---|
| offset | `ORDER BY x LIMIT n OFFSET m` | 上の行ズレ。ただし実装が最も簡単で、**任意位置へジャンプできる**（スクロールバーを掴んで飛ぶ） |
| keyset（カーソル） | 「最後に見た行の値」より後を引く | 行ズレに強いが**任意位置へ飛べない**（前から辿る前提）。実装も一段複雑 |
| スナップショット + offset | **読み取り時点を固定**して offset | 時点固定の仕組みがある系でしか使えない |

この系には有効期間型（SCD Type 2）が全テーブルに入っているので、**`as_of` を固定するだけで
3つ目が手に入る**。フィルタ確定時にサーバ時刻を1回もらい、以後の窓取得をすべて
`as_of=その時刻` で引けば、合間に何が更新されても窓の中身は動かない。offset の単純さと
ジャンプスクロール（総件数が分かれば7,000件目付近へ直接飛べる）を保ったまま行ズレが消え、
**keyset を実装する理由が無くなる**。「監査のために入れた仕組みが一覧スクロールの
安定性をタダで解決する」— 有効期間型を既定にした決定（§8-1）の思わぬ配当。

代償は「見ている一覧が固定時点のスナップショットになる」ことだが、これは欠点というより
意味が明確になっただけ（どのみち画面は取得時点の姿しか映さない）。**編集・再読込・
フィルタ変更で時点を取り直す**（=世代を進める）と決めれば運用は閉じる。論点B。

### 2-3. nuqs は何で、何でないか

nuqs は「**コンポーネントの状態を URL クエリ文字列に置く**」ライブラリ（`useState` の
URL 版。`useQueryState('confidence', parseAsArrayOf(...))` のように使う）。型付きパーサ
（数値・日付・enum・配列・JSON）、履歴の push/replace 制御、既定値の省略を持つ。
MIT・活発にメンテ（2026-08-08 確認）。公式アダプタは Next.js / **React SPA（Vite）** /
Remix / React Router / TanStack Router。

得られるのは「フィルタ状態が URL にある」ことの帰結そのもの:

- **絞り込んだ一覧を URL で共有できる**（「この一覧を見て」が Slack に貼れる）
- リロード・ブラウザ復元でフィルタが残る。戻る/進むがフィルタ操作を辿れる

一方、**nuqs はフィルタ UI を含まない**。どんな入力部品（確度のトグル、金額レンジ、
担当者の選択…）を並べるかは別の仕事で、「使いやすいフィルタ」の中身はそちらで決まる
（論点C）。nuqs が決めるのは状態の置き場だけ。

構造上の注意が1つ: nuqs が読み書きするのは `location.search`（URL の `?...` 部分）で、
**現在の FE はルーティングもクエリもハッシュの中に持っている**（`#/flows/sales?step=qualified`）。
場所が違う → 論点D。

### 2-4. REST / GraphQL のレイヤ論を、この系に当てはめる

参考コメントの区分はこう読める:

- **REST = ドメインのリモートファサード**。リソースと操作の意味をサーバ側が定義し、
  クライアントはその意味に従う。インタフェースの主導権がドメイン側にある
- **GraphQL = プレゼンテーションのためのデータ射影**。画面が必要とする形（この画面には
  この列とこの入れ子）をクライアントが宣言する。主導権が画面側にある

この区分自体は正しい。そのうえで、GraphQL が配当を払うのは主に次の構造があるとき:

- 画面の形が多様で増え続け、**画面ごとに BFF エンドポイントを掘る運用が破綻している**
- クライアントが複数ある（Web/モバイル/外部連携で必要なデータの形が違う）
- 複数のドメインサービスを1画面で合成する（例に挙がっていた決済+認証のような構成）
- スキーマが FE/BE **チーム間の交渉の契約**として機能してほしい

この系の現在地を重ねると:

- クライアントは**エンドユーザー FE 1つ**（管理画面 FE は未着手）。作り手は1人+AI
- バックエンドは1つで、**REST 面は手書きではなく定義から自動生成**される。
  「画面都合のパラメータを足すとドメイン API が汚れる」という古典的な緊張が、ここでは
  **パラメータ追加が全テーブルに一斉に効く**形になっていて成立しない。つまり
  “プレゼンテーション射影インタフェース”の役割を担う場所は既にあり、それは
  この自動生成面そのもの
- スキーマ契約の役割は、FE が定義を**値と型で import** している時点で（より強い形で）
  既に担われている

そして肝心の点: **グリッドが必要とする取得機能は、どちらの形態を選んでも同じだけ
実装しなければならない**。GraphQL は転送の形を変えるだけで、実装を1つも省いてくれない。

| グリッドが要るもの | REST での形 | GraphQL での形 |
|---|---|---|
| 窓取得 | `limit` + `offset` | Relay 型 connection（first/after） |
| 総件数 | レスポンスに `total` | connection の totalCount |
| サーバ側ソート | `sort=field:desc` | 引数 orderBy |
| サーバ側フィルタ | パラメータ語彙 → 条件式AST（論点C） | 引数 filter → 同じ AST |
| 時点固定 | `as_of`（**実装済み**） | 引数 asOf |

逆に、併用した側**だけ**に発生する実費がある:

1. **スキーマの動的生成** — `alt apply` のたびに GraphQL スキーマが変わる。生成器がもう1つ増える
2. **認可の強制ポイントが2経路になる** — リゾルバ経路にも認可4層+rowFilter を通し、
   REST と食い違わないことを保証し続ける（「FE に認可を複製しない」と同種の乖離リスクを
   サーバ内に作る）
3. **N+1 の塞ぎ直し** — 素朴なリゾルバは「一覧のクエリ本数は件数非依存」というフェーズ3の
   性質を壊す。dataloader で取り戻す実装が要る
4. **Go 移植の面積がほぼ倍になる** — TS 版は捨てる仕様（§8-1）。動的スキーマの GraphQL
   サーバは Go ではツーリングが薄く（gqlgen はコード生成前提）、移植の最難部になる

いま GraphQL が買えるものは「フィールド選択」と「FK の入れ子解決」程度で、どちらも
REST パラメータで表現できる（FK 経路の解決機構は条件式 AST が既に持っている）。

## 3. 論点と推奨

### 論点A: API 形態 — REST 拡張か、GraphQL 併用か（**決着: REST 拡張**）

**2026-08-08 決着 — REST 拡張で確定し、§8-1「一覧グリッド化の着手前に決めたもの」に
記録した**（旧 §8-2 論点16）。以下は判断の根拠として残す。

**推奨: REST 拡張。§8-1 の決定「API は REST 自動生成」を維持し、GraphQL は再訪条件つきで
見送る。** 根拠は §2-4 に尽きる — 必要機能はどちらでも作る、併用の実費（Go×2・認可2経路・
N+1 対策・スキーマ動的生成）は構造的、いま買えるものは REST パラメータで書ける。

参考コメントの期待値（レイヤの違いを正しく捉えて採用する）に対する answer は、
「この系では定義からの自動生成面が射影インタフェースの役割を内側に持っており、
射影の拡張がドメイン API を汚さないため、**分離の動機のほうが不在**」になる。

**再訪条件**（どれかが実際に起きたら、この論点を §8-2 に開き直す）:

1. 画面の種類が増え、一覧系パラメータの語彙が**表現力の壁**に当たる
   （「この画面のためだけの奇妙なパラメータ」が繰り返し生える）
2. クライアントが増える（管理画面 FE が別スタックになる、外部連携、モバイル専用画面）
3. Go 版が完成し、射影レイヤを**足す**変更が「捨てる予定の仕様を太らせる」変更でなくなる

**それでも併用するならこの形**: 読み取り専用の射影に限定し、書き込み・遷移・チェックは
REST のまま。「GraphQL リゾルバは REST と同じ内部関数（認可・クエリ組み立て）を通る」を
実装の完了条件にする。それでも実費 1〜4 のうち消えるのは 2 の一部だけ。

**後から導入する場合のコスト構造**（2026-08-08 の議論から）: GraphQL の後付けは安い。
後付け不能の有効期間型（記録しなかった過去は失われる）とも、後付けが高くつく認可
（既存の全面に横断条件を差し込む）とも違い、**保存していないデータを必要とせず、
既存画面に触らない追加の読み取り面**だから（併用は additive — 既存画面は REST のまま）。
導入費用（スキーマ生成・dataloader・認可2経路のテスト）は待っても増えない固定費で、
逆に**いま入れると TS と Go で2回作る**（TS 版は捨てる仕様）。Go 版完成後なら1回。
維持すべき条件は「認可・評価・時点・クエリ組み立てを HTTP ハンドラでなく内部関数に
集約し続ける」の1つだけで、これは Go 移植計画そのものが強制している（移植対象を
1箇所に集める設計 = GraphQL を後から挿せる設計）。論点C の「フィルタ語彙 → AST は
サーバ内部で組む」も同じ性質を保つ。ただし併用自体の恒常コスト（FE のデータ取得層と
エラー処理の流儀が2系統になる）は導入時期に依らず残る。また横断ダッシュボード到来時も
自動的に GraphQL ではない — その画面の主役は集計で、集計フィールドの実装はどちらでも
サーバの仕事。**再訪条件は「来たらこの論点をその画面の要求で開き直す」と読む**。

### 論点B: 取得 API の設計（REST 拡張の中身）

**推奨: `offset` + `total` + `sort` + フィルタ語彙 + `as_of` 固定（スナップショット世代）。**

- レスポンスを `{ records, total, offset, limit, asOf, now }` に拡張する。`now` は
  サーバ時刻で、**FE はこれを以後の窓取得の `as_of` に使う**（クライアント時計を信用しない）
- **世代（generation）**: フィルタ変更・ソート変更・再読込・編集成功で世代を進める =
  `as_of` を取り直し、`total` を引き直し、窓キャッシュを捨てる。世代内の窓取得はすべて
  同じ `as_of` → 行ズレなし（§2-2）
- 編集後に世代を進めるのは、固定時点のまま新しい行を1つだけ重ねると「同じ画面に
  2つの時点が混ざる」ため。窓1枚の再取得は安い（≦500行）。**編集した行がソート順の中で
  動く（金額順の画面で金額を直した等）のは仕様**とする
- ソートは単一キー `sort=expectedCloseMonth:asc`。**サーバが `id` をタイブレークに必ず足す**
  （これが無いと offset 窓の決定性が壊れる）。対象は deal 自身のフィールド + 現在ステップ
  （定義の宣言順を CASE で写す。論点G）。FK 先の名前でのソートは v1 では持たない
  （必要になったら `companyId.name` を許す。解決機構は既にある）
- 窓サイズは 100〜200（`MAX_LIMIT` 500 の内側）+ 先読み1窓程度。数字は実測で決める
- `fields=`（列の選択）は**やらない**。窓が小さいので全フィールド+`_flow` を返しても
  ペイロードは問題にならない。必要になったときの拡張余地とだけ記しておく

### 論点C: フィルタの表現 — URL 語彙・サーバ実装・UI

3つの層に分けると混ざらない。

**1. URL の語彙**（nuqs が持つもの）: **フィールド毎のパラメータ**にする。
条件式 AST の JSON を丸ごと URL に載せる案は捨てる（読めない・共有時に壊しやすい・
検証面積が広がる）。型ごとの定型:

| フィールド型 | パラメータ | 例 |
|---|---|---|
| enum | key の配列（IN） | `confidence=A,B` `status=open` |
| integer / yearMonth / date | `_gte` / `_lte` の対 | `monthlyProfit_gte=50000` `expectedCloseMonth_lte=2026-12` |
| text | 部分一致 | `title_like=看板` |
| FK（uuid） | 参照先 id の配列 | `ownerEmployeeId=me,<id>`（`me` = ログインユーザーの糖衣） |
| 現在ステップ | step key の配列 | `step=qualified,proposed` |

**2. サーバ実装**: パラメータ → 条件式 AST（`and` で束ねる）→ 既存の `compilePred` で
WHERE に落とす（`selectRecords` に `where?: Pred` を1つ足すだけ）。**フィルタの表現力 =
条件式 AST のサブセット**なので、SQL 変換・方言・適合テストの資産をそのまま使う。
検証は `alt validate` と同じ流儀 — 未知のフィールド・型に合わない値は
**400 + 直し方のヒント**で返す。

**3. フィルタ UI**（「使いやすい」の中身。nuqs の守備範囲外）: 営業一覧のフィルタ面として
**手で書く**。汎用フィルタビルダーは作らない（§4-3 の原則。DealForm を定義から
組み立てなかったのと同じ線）。ただし**候補・ラベル・型は定義から取る** — enum は
`{key, label}` からトグル群、step はフロー定義から、FK は masters から検索選択。
どのフィールドをフィルタ面に出すかだけが設計判断（全部出すと逆に使いにくい）。
v1 の当たり: **ステップ・担当（「自分の案件」を先頭に）・商材・確度・状態・見込み月レンジ**。

### 論点D: URL 状態の置き場 — nuqs とハッシュルータの同居

現状ルータはハッシュ式で、クエリも**ハッシュの中**にある（`#/flows/sales?step=qualified`）。
nuqs は `location.search`（ハッシュの外）を読み書きする。

| 案 | 形 | 評価 |
|---|---|---|
| **A. 同居**（推奨） | フィルタは本物の `?...`、ルートはハッシュのまま。`/?step=qualified&confidence=A#/` | ルータを触らず、公式の React（SPA）アダプタがそのまま使える。クエリがハッシュ航行を跨いで残るのは、一覧↔詳細の往復でフィルタが保たれる**利点**として効く（フロー参照画面に残るのは無害なノイズ） |
| B. 自作アダプタ | ハッシュ内クエリを読み書きするアダプタを書く | ルータ不変で URL の見た目も揃うが、nuqs の想定外領域を1枚挟む。最初に書くコードとしては筋が悪い |
| C. ルータ移行 | History API ルーティングに移行して標準形にする | いちばん素直だが、この仕事のスコープではない。フェーズ4の「画面が増えて分岐が辛くなったら入れ替える」の条件はまだ来ていない |

**推奨は A**。ただし着手初日に検証を3点置く: (1) nuqs がクエリ更新時に**ハッシュ部分を
保持するか**（README に明記なし）、(2) React 19 で警告なく動くか、(3) `hashchange` ベースの
`useRoute` と再レンダリングが干渉しないか。ここで欠陥が出たら **B ではなく C に倒す**
（B は負債の作り置き）。

補: **`as_of`（時点指定）も URL に寄せる**と「先月末時点のこの絞り込み」ごと共有できる。
いまはシェルの React 状態。nuqs に載せるのは小さい仕事なので、やるならこのタイミング。

### 論点E: グリッドの実装方式

要求から数式・列追加・条件付き書式・重複削除が**最初から落とされている**（§0）ので、
「スプレッドシートライク」の実体は次の集合まで縮む:

- 行の仮想描画（§2-1）
- セルのフォーカスモデル（クリック・矢印キーで移動。状態は `{行, 列}` 1つ）
- **Enter で編集開始 → セル位置に実 `<input>` / `<select>` をマウント → Enter 確定 / Esc 取消**
- Tab / Shift+Tab / 矢印での移動、確定後は下のセルへ

| 案 | 中身 | 評価 |
|---|---|---|
| **自前 + 仮想化ライブラリ**（推奨） | グリッド本体は手書き、仮想化だけ `@tanstack/react-virtual`（headless・UI を持たない） | 上の集合は小さな状態機械で、営業の一覧として特殊化し放題（§4-3 の原則どおり）。編集が実 DOM の input なので **IME が普通に効く** |
| フル機能グリッド（AG Grid / Glide Data Grid / react-data-grid 等） | 編集・キーボード・仮想化が最初から揃う | 範囲選択・コピペ・列操作まで要求が育ったら勝つ。ただし **UI を持つ共通部品**なので、部品の表現力が画面の上限になる構造（§4-3 が kintone の失敗構造と呼ぶもの）を FE の内側に持ち込む。canvas 描画系（Glide）はセルの自由なレンダリングと IME に癖 |
| 完全自前（仮想化も） | 行高固定なら translate の算数 | 書けるが、overscan・スクロール位置復元・端の処理は既知の罠が多く、ここで時間を使う価値が薄い |

判断基準を1つ言語化しておく: フェーズ4で「ルータ・状態管理・CSS フレームワークを
入れない」と決めた理由は概念の節約であって、依存ゼロ主義ではない。
**入れてよいのは「UI を持たない道具」（nuqs / react-virtual）、避けるのは「UI を持つ
共通部品」（フル機能グリッド）**と線を引くと、§4-3（部品の表現力が上限になる）と
矛盾なく繋がる。

範囲選択・コピペ・列リサイズ・列並び替えは v1 非対応と明記する（要求にも無い）。
aria は `role="grid"` の最小限（PC 中心・社内利用の決定に従う）。

### 論点F: 編集のセマンティクス

- **コミット単位はセル**（Enter 1回 = `PATCH` 1回 = 有効期間型の1バージョン）。
  監査・時点再現の思想にむしろ忠実で、「どの列をいつ誰が直したか」が版で残る。
  変更の文脈（どのステップで変わったか）は**既にサーバが `_flow_state` から引いて
  記録している**ので、グリッド側の追加実装は無い
- 行単位の「保存」ボタンは持たない（スプレッドシートライクの要求と矛盾する）
- **編集できないセル**は3種: `_permissions.record.write` が false の行（担当者+管理者
  以外）/ 計算列・フロー列（自社収益の合成・現在ステップ・未確認件数）/ v1 では FK セル
  （会社・担当の付け替えは詳細フォームに残す。検索つきセレクタはセルエディタの中で
  最も重く、頻度も低い）。読み取り専用は見た目でも分かるようにする
- セルエディタは型で決まる: text / integer → `<input>`、enum → `{key, label}` の
  `<select>`、date / yearMonth → 対応する input。**候補とラベルは定義から取る**
  （DealForm と同じ線）
- **競合**: いまの実装は「現在行を閉じられなかったら 409」+ 部分更新は**最新行への
  フィールド単位マージ**なので、別フィールド同士の同時編集は正しく合流する。
  同一フィールドの上書き（古い画面からの Enter）は last-write-wins だが、行を書けるのは
  **担当者+管理者だけ**（rowFilter）で、実運用の同時書き手はほぼいない。v1 はこのまま。
  必要になったら `PATCH` に「編集開始時の `_version.validFrom`」を precondition として
  渡し、違えば 409 → 行を再取得して知らせる、が安価な追加
- 編集成功 → レスポンスの行で置換 + 世代を進める（論点B）

### 論点G: フロー列 — グリッド化しても「フローの一覧」であり続けるか

普通の SFA のグリッド化なら列はテーブルのフィールドだけでよいが、この一覧の存在意義は
「フローに乗ったレコードの一覧」であること（現在ステップ・未確認件数。フェーズ4）。

- **現在ステップ・未確認件数の列は残す**。編集 → 自動判定が変わる → 未確認件数が変わる、が
  **一覧の上でそのまま見える**のがグリッド化の最大の追加価値（詳細画面で起きていた
  「データを直すと ☐ が ✓ になる」体験の一覧版。構想の中核が一覧で回るようになる）
- ステップのフィルタ（`step=`）は `_flow_state` を既に JOIN しているので WHERE 1つ。安い
- ステップのソートは定義の宣言順を CASE で写す（アルファベット順は無意味）
- 未確認件数でのソート・フィルタは v1 では持たない（SELECT 句の相関サブクエリ値なので
  WHERE で使うには一段の書き換えが要る。表示のみ）

## 4. この整理が置いている前提

崩れたら結論ごと見直す前提を明示しておく:

| 前提 | 依存している結論 |
|---|---|
| 社内利用・低トラフィック・案件1万件規模 | offset で足りる・窓再取得を気軽に打てる・COUNT が安い（論点B） |
| クライアントは 1 FE・作り手は1人+AI | GraphQL 見送り（論点A） |
| TS バックエンドは捨てる仕様で Go へ移植する | 併用の実費が倍、という論点Aの主要根拠 |
| 書き手が rowFilter で担当者+管理者に絞られている | 競合対策を v1 で持たない（論点F） |
| PC 中心 | キーボード操作中心・a11y 最小限（論点E） |

評価軸がここで閉じている保証はない。例えばオフライン編集・Excel からの貼り付け・行の
一括操作は**要求に無いため評価していない**。軸を足すときは §0 の要求に足してから
論点に反映する。

## 5. スコープ分割の案

読みと書きで独立に検証できるので、フェーズを2つに分ける（**フェーズ6・7 として確定**。2026-08-08）。

**先行タスク（両フェーズの前提）**: `alt seed --deals 10000` のような件数指定の
ダミーデータ生成。性能まわりの完了条件はこれが無いと検証できない。

**フェーズ6: グリッドの読み側** — サーバ: `offset` / `total` / `now` / `sort` /
フィルタ語彙 → AST（論点B・C）。FE: 仮想スクロール一覧（論点E の骨格）+ フィルタ面 +
nuqs（論点C・D）。完了条件の候補:

1. 1万件 seed で初回表示が体感即時（数値は着手時に決める）。スクロールで最後の1件まで到達できる
2. スクロールバーを掴んで中程へ飛んでも正しい行が出る（ジャンプ + 窓取得）
3. 窓取得の合間に別ユーザーが更新しても、行の重複・欠落が起きない（`as_of` 固定の検証）
4. フィルタ・ソートが URL に載り、**URL を別タブに貼ると同じ画面が再現する**
5. 未知のフィルタパラメータが 400 + 直し方のヒントで返る
6. 一覧に現在ステップ・未確認件数が出続けている（フェーズ4の完了条件を退行させない）

**フェーズ7: グリッドの書き側**（[phase-7-list-grid-edit.md](phase-7-list-grid-edit.md)）—
セルフォーカス・Enter 編集・型別エディタ・権限の反映（論点E・F）。完了条件の候補:

1. セルを矢印 / Tab で移動し、Enter → 編集 → Enter で確定できる（Esc で取消）
2. 確定が `PATCH` になり、**未確認件数のセルがその場で変わる**（例: 金額を入れると
   「見積金額が入っている」系の自動判定が充足に変わる）
3. 日本語入力（IME）の変換確定の Enter が、セル確定として誤発火しない
4. 担当外の行のセルは編集に入れない（見た目でも分かる）
5. enum セルは定義のラベルで表示・選択され、保存は key で行われる
6. 編集が版として残り、`as_of` で編集前の一覧が読める（既存機能の退行確認）

（完了条件の確定は着手時に `/phase-start` の流儀で行う — 上のリストはその素材）
