## 0. 要求

### 0-1. 背景 — kintone で実際に起きていたこと

エンドユーザーが**アプリ画面のスクリーンショットを撮り、画像に注釈を描いて**要望を出していた。

```
[案件詳細のスクショ]
   ↓ 赤ペンで
  「ここにフィールドを追加してほしい」
  「このフィールドがこういう条件のとき、こっちのフィールドを非活性にしてほしい」
```

これがエンドユーザーにも開発者にも負担だった、というのが出発点。

### 0-2. 要求

- **宣言的に要望を伝えられるフォーム**。「どのフローを変えるか」「新規フローの追加か」
  「こういう結果が欲しい」を構造として書ける
- 障害報告・改善要望・新機能提案を受け付ける
- **その要望が達成されたとき、業務フロー・フィールドがどう増減・移動するかが分かる**
- 起票者と起票後にやりとりできる**チャットUI**

### 0-3. 実現手段の希望

- 差分表示は**グラフィカル**が理想。ただし「できる範囲でよい」（＝ハード要求ではない）

### 0-4. この整理で明示的に落とすもの

| 落とすもの | 理由 |
|---|---|
| 要望から**自動で**定義を書き換える | 定義を書くのは AI + 人のレビュー（§5-1「定義ファイルが正」）。フォームは AI への入力であって、パイプラインではない |
| 投票・優先度スコアリング・SLA | エンドユーザーが数十人・要望が日に数件の規模で、順位付けの機構が要るほどの量にならない |
| 要望の全文検索 | 一覧のフィルタ（フェーズ6の機構）で足りる規模 |

## 1. 現状 — どこからの距離か

| いまあるもの | 事実 |
|---|---|
| 要望を書く場所 | **無い**。アプリ内に起票の口が1つも無い |
| チャット・コメント | **無い**。API はレコードの CRUD とステップ遷移だけ |
| 通知・未読 | **無い**。ナビにバッジの類が無い |
| 添付ファイル | **無い**。ストレージも配信経路も存在しない |
| 定義の版 | **無い**。`data/definitions.json` は常に最新の1枚。過去の定義は Git にしかない |
| 定義の差分 | **無い**。`alt diff` も `alt plan` も未実装（[implementation.md](../implementation.md) の「作らないもの」） |
| **共有語彙** | **ある**（フェーズ5）。フロー・ステップ・意図・出口条件・充足のしかた・使うデータが `#/flows/sales` に出ており、**営業がその語彙を読んでいる** |
| **グラフ描画** | **ある**。`apps/main/src/flows/flowGraph.ts` は純関数（後退辺検出・最長経路 rank・辺の種類分け）でテスト済み |
| **比較できる定義の形** | **ある**。`DefinitionBundle`（`{ tables, flows, roles }`）は `alt export` が JSON にする1つの値 |
| 追記型サブレコードの前例 | **ある**。`activity`（活動記録）は営業フローのどのステップからも書かれる。「フローの target にぶら下がる追記」の形は既にある |
| 認可 | フロー参加は「**どれかのステップの role であること**」から導出。ステップを担当しないロールは1件も読めない（§8-2 論点12、**未解決・優先度高**） |
| 一覧・グリッド | ある（フェーズ6・7）。要望一覧はこの機構にそのまま乗る |

**距離のまとめ**: 受付側（フォーム・一覧・チャット）は**定義を書けば大半が既存機構に乗る**。
差分側は**ゼロから**（版・比較・描画）。ただし比較の入力（`DefinitionBundle`）と
描画の土台（`flowGraph.ts`）は既にある。

## 2. 前提の解説

論点の手前に、判断に使う見方を置く。

### 2-1. スクリーンショット注釈は「下手なやり方」ではなく「最小コストのやり方」だった

まずここを取り違えると設計を間違える。**スクショ注釈が選ばれたのは、それがエンドユーザーに
とって最も安い方法だったから**であって、良い方法が思いつかなかったからではない。

スクショ + 赤ペンが運んでいた情報を分解すると:

| 運んでいたもの | 誰が払っていたコスト |
|---|---|
| ① **どの画面の話か** | 撮るだけ（ほぼゼロ） |
| ② **その画面のどの部品の話か** | 矢印を引くだけ（ほぼゼロ） |
| ③ そのときのデータの状態 | 撮るだけ（ゼロ。ただし写った範囲だけ） |
| ④ **どうしてほしいか** | 短い自由文（安い） |
| ⑤ なぜそうしてほしいか（背景・業務上の理由） | **書かれない**（高いので省略される） |
| ⑥ 開発者が定義のどこを直すかへの翻訳 | **開発者が全部払う**（画像を読み、業務を推測し、対象を特定する） |

**負担の非対称がここにある**。エンドユーザーは①②③をタダで送れるが⑤を落とし、
開発者は⑥を毎回払う。「エンドユーザーにも開発者にも負担」の中身は同じではない。

したがって置き換えの条件は「もっと構造化された、もっと重いフォーム」**ではありえない**。
それは①②の値段を上げて、⑤が書かれる保証も無い。**勝ち筋は次の形になる**:

- ①②③は**アプリが機械で添える**（人の入力をゼロのままにする）
- ⑤を**問いの立て方で引き出す**（「どうしてほしいか」ではなく「何ができなくて困っているか」を訊く）
- ⑥を**語彙の共有で消す**（対象を定義の名前で指せば、翻訳が要らなくなる）

### 2-2. 「宣言的」には2つの意味があり、両方が要る

要求の「宣言的な要望」は、実は2つの別々のことを指している。

| | 意味 | 置き換わるもの | どう実現するか |
|---|---|---|---|
| **参照の宣言性** | 対象を**座標ではなく名前**で指す。「画面のここ」ではなく「営業フローの提案ステップの出口条件」 | スクショ + 矢印（①②） | 定義の語彙をフォームの選択肢にする |
| **内容の宣言性** | **手段ではなく結果**を述べる。「フィールドを足して」ではなく「◯◯を記録できるようにしたい」 | 赤ペンの指示文（④） | 問いの立て方 + やりとりで詰める |

kintone の要望が「ここにフィールドを追加して」だったのは**手段の指定**で、
そのとき⑤（なぜ）が失われている。開発者は「本当にフィールドでよいのか」を判断できない。

⚠ **重要な非対称**: 参照の宣言性はフォームで**強制できる**（選択肢しか出さなければよい）。
内容の宣言性は**強制できない** — 人は放っておけば手段で書く。フォームでできるのは
「困っていること」を必須にし「こうしてほしい」を任意にする程度で、
残りは**やりとり（チャット）が引き受ける**。ここがチャットUIの本当の役割で、
「起票後の連絡手段」ではない。→ 論点C・H。

### 2-3. この系にはすでに共有語彙があり、しかも営業がそれを読んでいる

フェーズ5で `#/flows/sales` を作った結果、営業は次を画面で読めるようになっている:

- 業務フローとゴール / ステップとその**意図** / 遷移（前進・差し戻し・スキップ）
- 各ステップの**出口条件**と**充足のしかた** / この条件が**見ているデータ**
- この業務が**使うデータ**（テーブルと purpose）

**この機能はフェーズ5の直接の続き**として位置づけられる。フェーズ5が「読めるようにした」
語彙で、今度は「書けるようにする」。読めない語彙で書かせることはできないので、
**順序としてもフェーズ5が先で正しかった**。

kintone にはこの語彙が無かった（設定は管理画面の中にあり、エンドユーザーは見られない）。
だからエンドユーザーが指せる対象は画面の座標しかなく、スクショになった。
**スクショ注釈は kintone の構造の帰結であって、ユーザーの怠慢ではない。**

### 2-4. 定義バンドルは既に「比較できる形」をしている

差分を作るときに何を比較するかは、既に決まっている。

```ts
interface DefinitionBundle {
  tables: Registry          // Record<name, TableDef>
  flows: FlowDef[]          // steps[] / bindings[] / target / initial
  roles: RoleDef[]
}
```

- **構造が既知**（汎用 JSON diff ではなく、意味のある単位で比較を書ける）
- **同一性のキーが全部ある**（テーブル名・フィールド名・フロー key・ステップ key・
  出口条件 key）。フェーズ1〜5 で「ラベルをキーにしない」を徹底したことが、
  ここで**改名を削除+追加に見せない**という配当を払う
- `alt export` が JSON にするので、**2つのバンドルを比較する純関数**を書けば差分は出る

つまり差分の計算は「新しい仕組み」ではなく「既にある値を2つ並べる関数」。
難しいのは**計算ではなく提示**（何を、誰に、どの言葉で見せるか）。→ 論点E・F。

### 2-5. 要望の受付は、そのまま業務フローとして書ける形をしている

要望の処理は、この系の概念にきれいに対応する。

| 要望まわりの概念 | この系の何か |
|---|---|
| 要望（1件） | フローの **target レコード** |
| 起票 → トリアージ → 対応中 → 適用済 → 確認 | **ステップ** |
| 「対象が指定されている」「再現手順がある」 | **出口条件**（自動判定・手動チェック） |
| 起票者・対応者 | **ロール**と行レベル認可 |
| やりとり | target にぶら下がる**追記**（`activity` と同じ形） |
| 「未確認の要望が3件」 | 出口条件の一括評価（既存） |

**これは偶然ではない**。「システム改善依頼」は kintone でも実際に社内業務として回っていた
（スクショを撮って Slack に投げる、という運用も業務フローの一種）。
だから客先から見ればこれは**社内業務が1本増える**だけで、概念の濫用ではない。→ 論点A。

## 3. 論点と推奨

### 論点A: この機能自身を alt-kintone の定義として書くか（自己適用）

最初に決めるべき、全体の器の話。

| 案 | 形 | 評価 |
|---|---|---|
| **1. 客先定義に業務フローとして書く**（推奨） | `@alt/definitions` に `change_request` テーブル + `request` フローを足す | **基盤の変更がほぼゼロで動く**。認可・履歴・出口条件・一覧グリッド・フロー参照画面が全部そのまま効く。そして**構想の主張の自己証明**になる（「業務フローが第一級」なら、開発の業務フローも載るはず）。§10-3「客先アプリを作りながら共通部分を抽出」の実践そのもの |
| 2. プラットフォーム機構として作る | `_change_request` / `_change_message` を `_flow_state` と同じ層に置く | 客先定義を汚さない・`alt seed --reset` で消えない。しかし**状態遷移・認可・一覧を手で書き直す**ことになり（プラットフォームテーブルはフローに乗らない）、実装量が最大。自己証明の機会も捨てる |
| 3. 外部ツール（GitHub Issues 等） | アプリは起票フォームだけ持ち、API で Issue を作る | チャット・通知・添付・検索がタダで手に入る。しかし**営業は GitHub アカウントを持たない**ので、やりとりがアプリ内に見えない（＝チャットUIの要求を満たさない）か、双方向同期を書く羽目になる。同期は必ず壊れる |

**推奨は案1。** ただし案3の部分採用として、**対応側（定義変更の作業）だけ Git / PR に置き、
要望IDをコミットに書いて紐づける**（アプリ内が正、Git は作業の場）。

**案1 を採ると、基盤に足りないものが3つ露出する**（＝抽出すべき共通部分の候補）:

1. **「定義への参照」というフィールド型が無い** — 要望は「営業フローの提案ステップ」を
   指すが、フローもステップもテーブルの行ではないので `reference()` で表現できない。
   いまのままだと `targetFlow: text('対象フロー')` という**ただの文字列**になり、
   綴り間違いを `alt validate` が検出できず、フォームの選択肢が定義から生えない。
   → `definitionRef('flow' | 'step' | 'field' | 'check')` のような型が要る。
   **これは「参照の宣言性」（§2-2）の実装そのもの**なので、避けて通れない
2. **追記専用テーブルの扱い** — メッセージは版を積む対象ではない（論点H）
3. **開発データと実データの区別** — `alt seed --reset` が要望を消してよいのか（論点J の末尾）

⚠ **1 は「あったら便利」ではなく、この機能の中核が依存している。**
これが無いと要望フォームは「自由文の項目が多いフォーム」に退化し、スクショ注釈に対する
優位が消える。着手するなら最初のタスクになる。

### 論点B: 要望の対象を、どの粒度まで指させるか

「参照の宣言性」（§2-2）をどこまで細かくするか。細かいほど開発者の翻訳（⑥）が減るが、
起票者の負担（①②）が上がる。**§2-1 の原則から、上げてよいのは「選ぶだけ」の範囲まで。**

| 粒度 | 指す対象 | 起票者のコスト | 推奨 |
|---|---|---|---|
| 画面 | 案件一覧 / 案件詳細 / フロー参照 | **ゼロ**（いま見ている画面から起票すれば機械が入れる） | **必須・自動** |
| 業務フロー | 営業 | ほぼゼロ（画面から導出できる） | **必須・自動＋修正可** |
| ステップ | 提案 | 選ぶだけ（フロー参照画面で既に読んでいる語彙） | **任意** |
| 出口条件 | 「見積を提示した」 | 選ぶだけ | **任意** |
| データ項目 | 案件.見込み受注月 | 選ぶだけ（ただし57フィールドから選ばせるのは重い） | **任意・画面の項目から選ばせる** |
| 条件式の中身 | `deal.amount > 0` | **書けない** | **持たない** |

**推奨: 対象は「画面から自動で入る + 任意で1段階絞れる」。**
起票の必須項目は対象を含めてゼロにし、**書くのは困りごとの自由文1つだけ**にする。

⚠ **57フィールドのドロップダウンは作らない。** 「データ項目を指す」は、
**いま見ている画面に出ている項目**（案件詳細なら DealForm の項目、一覧なら列）から
選ばせる。これなら「矢印を引く」と同じ操作コストで、しかも名前で指せる。
＝ **スクショの②を、値段を上げずに宣言的にする**唯一の形。

### 論点C: 要望の種類と、種類ごとの問いの立て方

「内容の宣言性」（§2-2）はフォームで強制できないので、**問いの文面が設計そのもの**になる。

種類は**起票者が選ぶ**（開発者向けの分類ではなく、次の問いを変えるためのもの）:

| # | 種類（起票者向けの文言） | 続けて訊くこと |
|---|---|---|
| 1 | **記録したいことが記録できない** | 何を記録したいか／どの場面で使うか／例を1つ |
| 2 | **項目が分かりにくい・要らない** | どの項目か／どう困るか |
| 3 | **仕事の段取りと画面が合っていない** | どのステップか／実際はどうしているか |
| 4 | **次に進む条件が実態と合わない** | どの条件か／いま何が起きて困るか |
| 5 | **見え方・操作を変えたい** | どの画面か／何をしようとして手間取るか |
| 6 | **新しい業務を載せたい** | どんな仕事か／いまどこでやっているか／関わる人 |
| 7 | **壊れている（障害）** | 何をしたか／どうなると思ったか／実際どうなったか |
| 8 | その他 | 自由文 |

**すべての種類で必須は1つだけ**: 「**いま何ができなくて困っているか**」。
「どうしてほしいか」は**任意**にする — 訊けば手段で書かれる（§2-2）ので、
必須にすると⑤（なぜ）が押し出される。

**種類7（障害）だけは扱いが違う。** 障害は「期待と実際の乖離」で、要望は「期待の変更」。
混ぜると再現手順が失われる。分ける根拠は §2-1 の③にもあり、
**alt-kintone では③を機械で厚く添えられる**（論点D）。

⚠ 種類の選択を**必須にするか**は判断が要る。必須にすると入口が1段階増える。
推奨は**必須にする** — 続く問いが変わるので、選ばないと問いを出せない。
ただし「その他」を常に出し、迷ったら素通りできるようにする。

### 論点D: 機械が添えるコンテキスト — ここが「負担を減らす」の実体

§2-1 の①②③を人に払わせないための部分。**この機能の価値の半分はここにある。**

起票時にアプリが自動で持てるもの:

| 添えるもの | 出どころ | 何の代わりになるか |
|---|---|---|
| ルート（`#/deals/xxx`） | `useRoute` | 「どの画面か」（①） |
| 対象レコードID・案件名 | 画面の状態 | スクショに写っていた対象 |
| **現在ステップ・未充足の出口条件** | `_flow_state` / 一括評価 | 「なぜそこで困ったか」の状況証拠 |
| ログインユーザーとロール | `X-Dev-User` → 認証後は IdP | 「誰の立場での話か」 |
| 起票時刻 | サーバ時刻 | **`as_of` で当時の画面を再現できる**（③の完全版） |
| 定義の版 | 論点E で版を持てば | 「どの定義のときの話か」 |
| 直近の API エラー | シェルのAPIクライアント | 障害報告の決定打 |

⚠ **`as_of` は③の上位互換になる。** スクショは「写った範囲」しか残さないが、
有効期間型があるので**起票時刻を記録するだけで、当時のデータ状態を後から丸ごと引ける**。
「監査のために入れた仕組みが一覧スクロールをタダで解決した」（フェーズ6 §2-2）と同じ配当が
ここでも出る。**障害報告で「そのとき何が入っていたか」を訊き返す往復が消える。**

**推奨**: 起票の導線は**シェルに常設**（どの画面からでも1クリック）。押した瞬間に上表を
拾い、フォームには**読み取り専用の「この状況を添えます」ブロック**として見せる（黙って
送らない — 何が送られるか分かることが信頼の条件）。

### 論点E: 「差分」と呼ばれているものは3つあり、要る順番が違う

要求の「要望達成による増減・移動が分かる」を素直に読むと1つに見えるが、実装上は別物。

| # | 何の差分か | 見る人 | いつ | 版の仕組みが要るか |
|---|---|---|---|---|
| **1. 提案差分** | 要望に対して**こう変える予定**（未適用） | **起票者**と開発者 | 要望の対応中 | **要らない**（作業ツリーの定義 vs 適用済み `data/definitions.json`） |
| 2. 適用差分 | **変わりました**のお知らせ | 全員 | apply 後 | **要る**（版を積む） |
| 3. 版間差分 | 任意の2時点の比較 | 開発者 | いつでも | **要る** |

**推奨: 1 を先に作る。2・3 は後回し。**

理由は「版を積む仕組み（プラットフォームテーブル + `alt apply` の変更 + 保持方針）が
要らない」ことに尽きる。**要望に対する答えとして差分を見せる**という要求は、
「いまの定義」と「変更後の定義」の2つのバンドルがあれば満たせる。
フェーズ5 決定Iで見送った「定義の版と差分」の**需要側だけが先に来た**形になる。

計算は `@alt/diff`（新規パッケージ）の純関数1つ:

```ts
diffBundles(before: DefinitionBundle, after: DefinitionBundle): BundleDiff
```

意味のある単位で出す（汎用 JSON diff にはしない）:
テーブル追加/削除 / フィールド追加・削除・型変更・ラベル変更 / フロー追加 /
ステップ追加・削除・意図の変更 / 遷移（`next`）の変更 / 出口条件の追加・削除・
条件式の変更・`howTo` の変更 / バインディングの変更。

⚠ **提示は2種類要る。** 開発者向けは上の構造そのままでよいが、
**起票者向けは業務の言葉に翻訳する**（`FieldDef.type` が `integer` になったことを
営業に見せても意味がない）。既にラベル・intent・howTo が定義にあるので材料は揃っている。

```
この要望で変わること

業務フロー「営業（新規開拓）」
  ステップ「提案」
    ＋ 出る条件が1つ増えます
         「見積を提示した」（自動判定）
         → 案件に「一時金・請求額」を入れると充足します

データ「案件」
  ＋ 項目が1つ増えます
         「競合他社」（文字入力・任意）

いま入っている案件への影響                       ← 論点G
  ・新しい条件が未充足になる案件: 87 件
       （提案ステップにいて請求額が空のもの）
```

### 論点F: グラフィカルな差分をどう描くか

フェーズ5の `flowGraph.ts`（純関数・テスト済み）があるので、**遷移グラフの差分は安い**。
ただし素朴にやると読めなくなる罠が1つある。

⚠ **前後の2枚を並べて描くのは失敗する。** ノードを1つ足すと rank が変わり、
**関係ないノードまで全部動く**。人間は「動いたもの」を「変わったもの」と読むので、
何が変わったのか分からなくなる。

**推奨: 合併グラフを1枚描く。**

- ノード集合 = 旧 ∪ 新。各ノード・各辺に `added` / `removed` / `changed` / `unchanged` を持たせる
- **rank の計算は新側の定義で行う**（削除ノードは「前任者の rank + 1」を借りる）
  → 残るノードの位置が動かない
- 描き分け: 追加=実線＋強調、削除=点線＋取り消し、変更あり=枠を変える

```
┌─ 遷移（変更後） ────────────────────────────────┐
│                                                  │
│  接触 ──→ ヒアリング ──→ 提案 ──→ ┏━━━━━┓      │
│                            │        ┃稟議 ┃ ＋   │
│                            └───────→┗━━━━━┛      │
│                                        │         │
│                            ┈┈┈┈┈┈┈┈┈┈┈┈┈↓        │
│                            （提案→受注は無くなる）│
│                                      受注        │
│  ＋ 追加   ┈ 削除   ◆ 条件が変わった             │
└──────────────────────────────────────────────────┘
```

実装は既存を壊さず `flowGraphDiff(before, after)` を別に足す（`flowGraph()` を2回呼んで
合成する）。**グラフが苦しくなったら捨ててリストにできる**という phase-5 の逃げ道も同じく残す。

⚠ **フィールドの「移動」は現状の定義では表現できない**（要求に明示されているので重要）。
`TableDef.fields` は `Record<string, FieldDef>` で、**表示順を持っていない**。
画面の並びは `DealForm.tsx` の JSX の手書き順。しかも Record は
**Go の map で反復順が不定になる** — enum 候補を `Record` から配列に変えた
フェーズ5 決定B とまったく同じ問題が、fields 側に残っている（enum のときは
FE が候補を回していたので発覚したが、fields は手書きなので発覚していない）。

→ 「フィールドの移動が分かる差分」を作るなら、先に**定義がフィールドの順序を持つ**必要がある。
これは定義側の変更（`fields` を配列にするか、順序を別に持つか）で波及が広い。
**この整理では「移動は v1 のスコープから外し、増減だけ出す」を推奨**し、
順序を持たせるかは独立した判断として §6 に残す。

### 論点G: 適用前に「既存データへの影響」を数えられる（構想の配当）

これは要求に無いが、**この系だからできることで、しかも安い**ので論点に上げる。

出口条件は SQL に変換できる範囲に限られている（§8-1）。したがって
**新しい定義の条件式を、いまのデータに対して評価できる**。

- 「この出口条件を足すと、**いま提案ステップにいる 214 件のうち 87 件が未充足になる**」
- 「このステップを消すと、**いまそこにいる 12 件の行き先が無くなる**」
- 「この必須項目を足すと、**既存 1,203 件のうち 340 件が空のまま**になる」

kintone には原理的にできない（設定変更の影響を事前に見る手段が存在しない）。
`alt plan` が「DB に何が起きるか」を出すのに対し、これは「**業務に何が起きるか**」を出す。
§5-4 の「業務フローの変更を影響つきでレビューできる」という差別化点の、
**エンドユーザーに見える形**がこれになる。

**推奨: 提案差分の一部として作るが、v1 は「新しい出口条件の未充足件数」1種類に絞る。**
実装は CLI 側（`alt` は既に DB に触る）で計算し、結果を要望レコードに書く形が素直
（サーバに新旧2つの定義を持たせなくて済む）。

⚠ ただし §8-2 論点17（一覧の性能は条件式が何を読むかで決まる）と同じコスト構造を持つ。
1万件 × 新条件の評価になるので、**適用前に1回叩くバッチ**であって画面から毎回打つものではない。

### 論点H: やりとり（チャット）のデータモデルと、更新の伝え方

**チャットの役割は「起票後の連絡」ではなく「内容の宣言性を詰める場」**（§2-2）。
最初の起票は自由文1つでよく、**構造は往復で埋まっていく**という設計になる。

**データモデル**:

| 案 | 評価 |
|---|---|
| **1. 業務テーブルとして定義に書く**（推奨） | `change_request_message` を要望フローの primary にする。`activity` と同じ形（target にぶら下がる追記）で、**前例がある**。API・認可・一覧が既存のまま効く |
| 2. プラットフォーム機構（`_message`） | 汎用になるが、認可と API を手で書く。案1 で足りないと分かってから |

⚠ **有効期間型（SCD Type 2）との噛み合わせ**: メッセージは状態ではなく出来事なので、
版を積む対象ではない。ただし**更新しなければ版は1つのまま**なので害は無く、
むしろ「メッセージを編集したら編集前が残る」は望ましい。**v1 は業務テーブルのままでよい。**
（§4-1「業務イベントはドメインモデルとして別に持つ」と整合する — これは業務イベント側）

**更新の伝え方**:

| 案 | 評価 |
|---|---|
| **ポーリング**（推奨） | 要望の詳細を開いている間だけ 5〜10 秒間隔。社内・低トラフィック・要望は日に数件。**サーバ変更ゼロ** |
| SSE | Go でも自然だが、いま要る理由が無い |
| WebSocket | 重い。この規模で採る理由が無い |

**未読は要る**（返信に気づかないとチャットは死ぬ）。ナビに未読件数のバッジ。
「ユーザー × 要望 × 最終閲覧時刻」を持てばよく、これも業務テーブルで足りる。

⚠ **未読バッジはシェルの仕事**（§4-3「共通化するのはシェルだけ」）。
業務画面の中に置くと、要望画面を開いていないと気づけない。

### 論点I: 添付ファイル — スクリーンショットを禁止できるか

**できないし、してはいけない。** 宣言的なフォームが目指すのは
「スクショが**唯一の**チャネルである状態」を終わらせることであって、
スクショを禁じることではない。UI の細かい崩れなど、画像が最短の場面は残る。

一方で添付の実装コストは低くない（ストレージ・配信・認可・容量管理）。現状ゼロからになる。

**推奨: v1 では添付を持たない。** 代わりに論点D（機械が添えるコンテキスト）を厚くする。
**再訪条件**を明記しておく: 「画像がないと伝わらない」要望が実際に3件出たら作る。
そのときの最小形は「チャットに画像を貼れる」だけ（フォームには不要 — 起票を重くしない）。

⚠ ブラウザ内で画面を自動キャプチャする（html2canvas 等）案は**採らない**。
依存が重く、描画が再現しないことが多く、そして何より**論点Dのほうが情報量が多い**
（画像は「見えている範囲」だけだが、コンテキストは `as_of` でデータ全体を指す）。

### 論点J: 認可 — この機能は §8-2 論点12 を踏み抜く

**ここが着手前に解く必要のある唯一の依存。**

要望フローを定義として書くと（論点A 案1）、認可は「どれかのステップの role であること」から
導出される（§4-1）。ところが:

- **起票するのは全員**（営業・営業マネージャー・制作・MEO運用）。
  ステップの `role` は**1つしか持てない**ので、起票ステップの role を `sales_rep` にすると
  **制作担当が要望を1件も起票できない**（読むこともできない）
- 対応するのは開発者。**開発者は客先の従業員ではない**が、`employee` に行が要る（§8-2 論点13）

`packages/server/src/authz.ts` を読むと、塞がれ方は**2箇所**で、性質が違う（2026-08-08 確認）:

| 層 | 実装 | 要望フローで何が起きるか |
|---|---|---|
| フロー参加 | `participates` = `isAdmin \|\| flow.steps.some(s => s.role === principal.role)` | **どのステップの role でもないロールは、一覧ごと 403**。制作担当は要望を1件も読めない |
| ステップ操作（遷移） | `permissionsOf` の `advance` = `update && (isAdmin \|\| role === 現在ステップの role)` | **起票者が自分の要望を次へ進められない**（起票ステップの role が1つしか無いため） |
| レコード更新 | `update` = access ∧ rowFilter ∧ ¬historical。**現在ステップの role には縛られない** | ここは問題にならない（`rowFilter` で「起票者本人」にすればよい） |

⚠ **この2つは `viewers` では解けない。** 論点12 が §8-2 に書かれた形（営業マネージャーが
「操作しないが見る」）はフローに `viewers: [role]` を足せば済むが、要望フローが要るのは
**同じステップを複数のロールが操作する**ことで、読みだけ通しても遷移が通らない。
→ **論点12 は実は2つの別々の要求を1つの番号に畳んでいる**。着手時に分けて設計する。

つまり**この機能は §8-2 論点12（ステップを担当しないロールはフローに参加できない）の
最小かつ最も切実な実例になる**。営業マネージャーが一覧ごと 403 になるのと同じ穴に、
今度は「全社員が起票する業務」が落ちる。

| 案 | 評価 |
|---|---|
| **論点12 を先に解く**（採用） | 候補は「フローに `viewers: [role]` を足す」「ステップの role を配列にする」「ロール階層」。**要望フローは "全ロールが参加する業務" という、いままで無かった形**なので、論点12 の設計を検証する良い題材になる |
| 要望フロー専用の例外を作る | 導出をやめて要望フローだけ別扱いにする。**「認可は業務フロー定義から導出する」という確定事項を最初に破る**ことになる。採らない |
| ロールを持たない起票用の口を作る | 同上。認可の穴になる |

**決着（2026-08-08）: 論点12 を独立したフェーズ8として先に解く。**
この仕事の T1 に畳み込まない。理由は3つ:

1. **要望受付と無関係に既に価値がある** — 営業マネージャーが案件一覧ごと 403 のまま
2. **認可モデルは基盤の中心**で、要望受付の都合で設計すると歪む
3. 上の (a)/(b) のどちらをどう解くかで**この仕事のタスク表が変わる**ので、混ぜると詳細化を2度やる

→ [phase-8-authz-participation.md](phase-8-authz-participation.md)

補: **開発データと実データの区別**。`alt seed --reset` は全テーブルを消す。
要望が消えると困る（本物のやりとりが入る）ので、`--reset` の対象から外すか、
要望は別のDBファイルにするか、決めが要る。小さいが忘れると痛い。

### 論点K: AI をやりとりの当事者に入れるか

構想は「アプリを作るのは人間ではなくAI」なので、**要望を詰める往復に AI が入るのは自然**。
「その要望は提案ステップの出口条件の話ですか？」と訊き返せれば、
内容の宣言性（§2-2）が自動で上がる。

**推奨: v1 では入れない。ただし入れる場所だけ空けておく。**

- 入れると LLM 呼び出し・APIキー管理・コスト・プロンプト設計が一度に乗る。
  **要望受付が動くかどうかとは独立した検証**なので、混ぜると両方の評価ができない
- 空けておくコストはゼロに近い: メッセージに `authorKind: 'human' | 'ai'` を持たせるだけ

⚠ この判断は「AI前提の業務アプリ基盤」という構想の中で**いちばん筋の良い AI の入れどころ**を
先送りしている、という自覚は持っておく。動いてから最優先で戻る候補。

## 4. この整理が置いている前提

崩れたら結論ごと見直すもの:

| 前提 | 依存している結論 |
|---|---|
| エンドユーザーは客先の社員のみ・数十人規模 | ポーリングで足りる（論点H）／投票・優先度が要らない（§0-4） |
| 要望は日に数件程度 | チャットの同期要件が緩い／全文検索が要らない |
| 定義変更のリードタイムは「その日〜数日」 | 提案差分を見せる相手が起票者本人でいられる（論点E）。即時反映を期待されるなら別設計 |
| 開発者は1人 + AI で、Git を使う | 対応側を PR に置ける（論点A の案3 部分採用） |
| 客先の営業は GitHub アカウントを持たない | 外部ツール全面採用の否定（論点A 案3） |
| 起票者が `#/flows/sales` の語彙を読める | 参照の宣言性が成立する前提（§2-3）。**フェーズ5 が効いているかどうかが、この機能の成否を直接決める** |

⚠ 最後の前提は**未検証**。フェーズ5 の完了条件は「異動者が定義ファイルなしで業務を把握できる」
だったが、**実際に営業が読んだ**わけではない。ここが成立していないと、
語彙で対象を指させる設計そのものが崩れる。→ 着手前に確認する価値がある（§6）。

評価軸がここで閉じている保証はない。例えば **要望の棚卸し・却下の伝え方・
「同じ要望が既に出ている」の検出**は、要求に無いため評価していない。

## 5. スコープ分割の案

**この仕事は2つに割れる。しかも互いに独立して価値がある。**

```
（フェーズ8: ロールと参加の認可 ＝ 前提）
                        │
        ┌───────────────┴───────────────────────┐
        ▼                                       ▼
フェーズ9: 要望の受付とやりとり        フェーズ10: 定義の差分
  起票フォーム（語彙で指す）             2バンドルの比較（純関数）
  コンテキスト自動添付                   業務の言葉での提示
  要望の一覧・詳細                       合併グラフ
  チャット・未読                         既存データへの影響件数
        │                                       │
        └───────────────┬───────────────────────┘
                        ▼
              要望に提案差分が紐づく
```

- **フェーズ9 は差分が無くても成立する**（要望を受け、やりとりし、対応する）
- **フェーズ10 は要望が無くても成立する**（定義変更のレビュー・お知らせに使える）
- 順序はどちらからでもよいが、**9 → 10 を推奨**（要望の実物が無いと、
  差分を「誰にどの言葉で見せるか」が決まらない。§2-1 の教訓 —
  実際の負担の形を見ずに設計すると重いフォームを作る）

### フェーズ9（要望の受付とやりとり）の完了条件の候補

1. **どの画面からでも1クリックで起票でき、必須入力は困りごと1つだけ**
2. 起票された要望に、**画面・フロー・ステップ・対象レコード・起票時刻・ロールが自動で入っている**
3. 対象を**定義の語彙で**（フロー / ステップ / 出口条件 / いま見えている項目から）指定できる
4. **営業・制作・MEO運用のいずれのロールでも起票でき、自分の要望を読める**（＝論点12 が解けている）
5. 要望の一覧が既存のグリッドで読め、**種類・状態・起票者で絞れる**
6. 起票者と対応者がやりとりでき、**返信が未読としてナビに出る**
7. 要望が業務フローとして動く（起票 → トリアージ → … の遷移と出口条件）
8. `pnpm verify` が通る

### フェーズ10（定義の差分）の完了条件の候補

1. 2つの定義バンドルの差分が**意味のある単位で**出る（純関数・テスト付き）
2. 差分が**業務の言葉で**読める（型名や列名ではなく、ラベル・intent・howTo で）
3. 遷移の変更が**合併グラフ1枚**で読める（追加・削除・変更の描き分け／残るノードが動かない）
4. **新しい出口条件を入れたときの未充足件数**が適用前に出る
5. 差分が要望に紐づいて、起票者が「自分の要望でこう変わる」を読める

⚠ **整理の記述を1つ訂正する。** 論点A は「（`definitionRef` が無いと）綴り間違いを
`alt validate` が検出できず」と書いているが、**`alt validate` は定義を検証する道具で、
要望レコードの値（データ）は見ない**。値を弾くのはサーバの `validateInput`
（`record-input.ts`）で、`enum` の候補チェックと同じ場所になる。`definitionRef` の
配当は「validate が拾う」ではなく次の3つ:

1. **サーバが値を定義レジストリと突き合わせて弾ける**（`enum` と同じだが、候補が
   テーブル定義ではなく**定義バンドル全体**から来る）
2. **FE が対象を業務の言葉で表示できる**（`sales.proposed.timing_confirmed` →
   「営業（新規開拓） ＞ 提案 ＞ 導入時期を確認した」）。FE は定義を値として持っている
3. **定義そのものが「この列は定義を指す」と知っている** — フェーズ10 で
   「消そうとしているステップを指している要望が3件ある」を出す足場になる

### 7-1. プラットフォームに足すもの（自己適用で露出した穴）

論点A は「案1 を採ると基盤に足りないものが3つ露出する」と予告していた。
実際に着手すると**4つ**だった。3つ目（開発データと実データ）は決定D で畳んだので、
このフェーズで**作るのは2つ**。

#### (1) 定義への参照 — `definitionRef`（論点A の 1、決定A）

```ts
// packages/dsl/src/table.ts
export const DEFINITION_REF_KINDS = ['table', 'flow', 'step', 'field', 'check'] as const
export type DefinitionRefKind = (typeof DEFINITION_REF_KINDS)[number]

export function definitionRef(kind: DefinitionRefKind, label: string): FieldBuilder
// → { type: 'text', label, definitionRef: kind, required: false, primaryKey: false }
```

**値は定義の中で一意になる合成キー**（区切りは `.`）。兄弟フィールドを見ないと
解決できない形（ステップキーだけを持つ）にしない — サーバもFEも1つの値だけで解ける。

| kind | 値の例 |
|---|---|
| `table` | `deal` |
| `flow` | `sales` |
| `step` | `sales.proposed` |
| `field` | `deal.expectedCloseMonth` |
| `check` | `sales.proposed.timing_confirmed` |

解決は **`@alt/dsl` の純関数1つ**にして、サーバ（値の検証）とFE（表示）が同じものを使う。
`compilePred` を validate とサーバが共有しているのと同じ形。

```ts
export interface DefinitionRefTarget {
  kind: DefinitionRefKind
  /** 業務の言葉。['営業（新規開拓）', '提案', '導入時期を確認した'] */
  labels: string[]
}
export function resolveDefinitionRef(
  defs: { tables: Registry; flows: readonly FlowDef[] },
  kind: DefinitionRefKind,
  value: string,
): DefinitionRefTarget | undefined
```

#### (2) サーバが埋める作成時刻 — `fill: 'createdAt'`（決定G）

**穴の中身**: 有効期間型は `_version.validFrom` を持つが、これは**現在バージョンの**
開始時刻なので、更新するたびに動く。要望は起票後に対応者・ステップが変わるので、
`validFrom` は起票時刻ではなくなる。作成時刻を1クエリで読む手段が無い。

これは完了条件2（起票時刻が自動で入る）とメッセージの並び順の**両方**を塞ぐ。
逃げ道は「FE が `new Date()` を送る」だが、**クライアント時計を信用しない**という
フェーズ6 決定A（`snapshot` はサーバの `now` を使う）と正面から矛盾する。

```ts
// packages/dsl/src/table.ts
export const FIELD_FILLS = ['createdAt'] as const
export function createdAt(label: string): FieldBuilder
// → { type: 'datetime', label, fill: 'createdAt', required: true, primaryKey: false }
```

- `validateInput`: `fill` があるフィールドは**入力として拒否**し、必須チェックからも外す
  （`primaryKey` と同じ扱い）
- `createRecord`: `ctx.now` を入れる。**更新では触らない** — `updateRecord` は
  現在行の値を引き継ぐので（`records.ts:343`）自然に保たれる
- `alt seed` は `insertRecord` を直接呼ぶ開発用の裏口なので、明示的に値を渡す

⚠ **`fill` を「デフォルト値」の一般機構にしない。** `'createdAt'` の1値だけ。
一般化すると式や関数を持ち込むことになり、「定義はただの JSON」（§4-0）が崩れる。

#### (3) 業務フロー描画をシェルへ（決定H・論点L）

**2本目のフローを載せる初めての機会**なので、§4-3「共通化するのはシェルだけ」が
実際に何を指すのかがここで決まる。

| 案 | 評価 |
|---|---|
| L1. 要望用にコピーして書く | §4-3 の字義どおり。ただし `ExitChecklist` / `AdvanceButtons` / `StepTrack` が描いているのは **`_flow`（APIレスポンスのメタ）だけ**で、案件の語は1つも出てこない。コピーすると同じものが2本になり、3本目で必ず崩れる |
| **L2. `_flow` を描く部分だけシェルに上げる**（推奨） | **kintone の失敗構造は「一覧とフォームが共通部品の表現力に縛られる」ことで、フロー描画ではない**。むしろ「業務フロー定義はUIに現在地表示 + 出口条件チェックリスト + 遷移制御として現れる」（§8-1 確定事項）は**1つの機構**として書かれている。一覧・フォームは各フローで手書きのまま |

**決着: L2**（2026-08-09、着手時にレビューで確定）。移すのは
`StepTrack` / `ExitChecklist` / `AdvanceButtons` の3つで、
入力は `_flow`（`{ step, stepName, exit[], unsatisfied, next[] }`）と `_permissions` と
コールバックだけ。**テーブル名もフィールド名も知らない**ことを境界にする。

⚠ **一覧（`DealList`）とフォーム（`DealForm`）は絶対に上げない。** ここを上げた瞬間に
kintone と同じ構造になる。境界は「`_flow` を描くか、業務データを描くか」。

#### フロー1本（`packages/definitions/src/flows/request.ts`）

```
                 ┌──────── 差し戻し ────────┐
                 ▼                          │
  起票(filed) ──→ 受付(triaged) ──→ 対応中(in_progress) ──→ 適用済(applied) ──→ 完了(closed)
      │                │                       ▲                   │
      └────────────────┴──→ 見送り(declined)   └───────────────────┘
```

| ステップ | 担当 `roles` | 出口条件 |
|---|---|---|
| `filed` 起票 | **`ROLE_KEYS`**（全員） | auto `target_specified`「対象が指定されている」（`targetFlow` が入っている）／ manual `reproduction_written`「壊れているなら、何をしてどうなったかが書いてある」 |
| `triaged` 受付 | `['admin']` | auto `assignee_set`「対応者が決まっている」／ **auto `replied`「起票者に返信した」**（`change_request_message` の exists） |
| `in_progress` 対応中 | `['admin']` | manual `definition_changed`「定義を変更して適用した」 |
| `applied` 適用済 | **`ROLE_KEYS`** | manual `confirmed_by_reporter`「起票者が解決を確認した」 |
| `closed` 完了 | `['admin']` | （終端） |
| `declined` 見送り | `['admin']` | （終端） |

- `target`: `change_request` / `initial`: `filed` / `viewers`: **無し**（全員が operator）
- `rowFilter`: `change_request` は**起票者本人**、`change_request_message` は**投稿者本人**、
  `change_request_read` は**本人**。管理者はバイパスする
- bindings: 3本とも `primary`。`employee` は `global` なので宣言不要（reads に出す）

⚠ **`replied` は「データを直すと自動判定が勝手に充足に変わる」を、要望フローで再現する**。
`activity` の exists で営業の出口条件を判定しているのと同じ形を、メッセージで書く。
構想の中核が2本目のフローでも働くことの検証になる。

⚠ **`advance` の効き方を確認済み**: `filed` の `roles` が `ROLE_KEYS` でも、
`advance` は `update`（= rowFilter）も要求するので、**進められるのは起票者本人と管理者だけ**
（`authz.ts:211`）。「全員が操作するステップ」と「自分の起票だけ触れる」が両立する。

### 7-3. FE の形

```
apps/main/src/
  shell/
    flow/                        ← 新規。_flow を描くだけ（決定H）。業務の語を持たない
      StepTrack.tsx              ← flows/sales/ から移動
      ExitChecklist.tsx          ← 同上
      AdvanceButtons.tsx         ← 同上
    RequestButton.tsx            ← 新規。ヘッダ常設の起票導線（論点D）
    UnreadBadge.tsx              ← 新規。ナビの未読（論点H）
  flows/
    sales/ …                     ← import 元が変わるだけ
    request/                     ← 新規
      RequestNew.tsx             ← 起票フォーム（コンテキスト自動添付）
      RequestList.tsx            ← 素直な表 + フィルタ（決定I）
      RequestDetail.tsx          ← 現在地 + チャット
      RequestChat.tsx
      requestContext.ts          ← ルート → 対象の導出（純関数・テストする）
```

- **ルータ**: `#/requests` / `#/requests/new?from=<起票元のハッシュ>` / `#/requests/:id`
- **APIクライアント**: `createClient(auth, flow)` は**フローを1本に固定している**
  （`api.ts:109`）。シェルが**フローごとに1つずつ作る**（`clients.sales` / `clients.request`）。
  呼び出しごとに `flow` を指定できるようにはしない — `flow` は認可の範囲と `changed_flow` を
  決める値なので、指定漏れが**認可の範囲の取り違え**になる
- **起票の導線**: ヘッダに常設。押すと現在のハッシュを `from=` に載せて
  `#/requests/new` へ。⚠ **画面の状態を業務画面からシェルへ push しない** —
  `from` から対象テーブル・レコードIDを導き、**フォームがサーバから現在ステップと
  未充足条件を引く**（`requestContext.ts` が純関数、取得は既存API）。
  シェルと業務画面の結合を作らずに論点D の表を全部埋められる
- **添えるものは読み取り専用で見せる**（論点D の推奨。黙って送らない）
- **対象のデータ項目**は、対象テーブルのフィールド全部から選ばせる。
  論点B の「57フィールドは重い」は**テーブル横断の話**で、`deal` 単体は21件。
  画面に見えている項目だけに絞るのは、定義がフィールドの順序と可視性を持ってから（決定C）
- **未読**: シェルが要望メッセージと自分の既読行をポーリング（10秒）し、
  **FE で突き合わせる**。⚠ 集計APIが無いので `limit=500` の全件取得になる。
  要望が数百件を超えたら方式ごと見直す（一覧の名前解決と同じ制約。フェーズ6 決定F）
