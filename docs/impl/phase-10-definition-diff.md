# フェーズ10: 定義の差分

**「この要望でこう変わります」を、業務の言葉で、適用する前に見せる。**

フェーズ9 で要望が業務フローとして回りはじめた。返ってくるのが「直しました」の一文だと、
起票者は自分の要望がどう解釈されたか分からない。ここで作るのは**その返事の中身**にあたる。

- 整理の出どころ: [phase-9-change-requests.md](phase-9-change-requests.md) §3 論点E・F・G、§5（スコープ分割）
- 合流するもの: フェーズ5 決定I で見送った「定義の版と差分」（§8-2 論点5）
- 前提になっている未決着: §8-2 論点18（定義がフィールドの順序を持たない）→ §3 論点G で扱う

---

## 0. 要求とスコープ

### 0-1. 要求（phase-9 §0-2 から引き継いだもの）

> 要望が達成されたとき、**何がどう増減・移動したのかが分かる**こと。
> それが**起票した営業に分かる言葉**で出ること。

### 0-2. 「差分」は3つあり、要る順番が違う（phase-9 論点E）

| # | 何の差分か | 見る人 | 版の仕組み | このフェーズ |
|---|---|---|---|---|
| **1. 提案差分** | **こう変える予定**（未適用） | **起票者**と開発者 | **要らない** | **作る** |
| 2. 適用差分 | 変わりましたのお知らせ | 全員 | 要る（版を積む） | 作らない |
| 3. 版間差分 | 任意の2時点の比較 | 開発者 | 要る | 作らない |

1 だけで要求は満たせる。**「いまの定義（適用済み）」と「変更後の定義（作業ツリー）」の
2つのバンドルがあれば計算できる**ので、プラットフォームテーブルも `alt apply` の変更も要らない。

### 0-3. 明示的に落とすもの

| | 理由 |
|---|---|
| 版を積む仕組み（`_definition_version` 的なテーブル） | 上の 2・3 のためだけに要る。1 には不要 |
| **フィールドの「移動」** | §3 論点G。**画面の並びは定義から出ていない**ので、順序差分を出しても画面は何も変わらない |
| 定義の自動書き換え（要望から定義を生成する） | phase-9 §0-4 で落としたまま。差分は**人（とAI）が書いた変更**を説明するもの |
| 差分から生成する FE の更新（`alt diff --since-generated`、§4-4） | 別の軸。§3 論点H |
| 破壊的変更の可否判定 | `alt apply` の `--recreate` ガードが既に持っている。二重に持たない |

## 1. 現状 — どこからの距離か

**材料はほぼ揃っている。** 足りないのは「比べる関数」と「見せる場所」だけ。

| 要るもの | いまあるか |
|---|---|
| 比較する2つのバンドル | **ある**。`data/definitions.json`（適用済み）と `loadBundle()`（作業ツリー）。`DefinitionBundle` は `{tables, flows, roles}` の素の JSON（`packages/dsl/src/bundle.ts`） |
| 業務の言葉 | **ある**。`label` / `intent` / `howTo` はすべて定義が必須で持っている（フェーズ5） |
| 遷移グラフのレイアウト | **ある**。`layoutFlow()`（純関数・テスト付き）。ただし置き場が `apps/main`（§3 論点D） |
| 条件式が見ているデータ | **ある**。`referencedFields()`（フェーズ5 決定D） |
| 件数を数える SQL | **ある**。`countRecords()`（フェーズ6）。`flow` / `steps` / `where` を取る |
| 要望に何かを添える場所 | **無い**。`change_request` に変更案を持つ列が無い（§3 論点E） |
| 差分を描く画面 | **無い**。`GraphSvg` は `FlowReference.tsx` の中に閉じている（§3 論点D） |

## 2. 前提の解説

### 2-1. 差分は「解決済みの言葉」で持たないと、あとで読めなくなる

これがこのフェーズでいちばん効く前提。

提案差分は**適用されたら消える**。`alt apply` のあとは作業ツリーと適用済みが一致するので、
同じ計算をしても何も出ない。にもかかわらず起票者は「自分の要望で何が変わったのか」を
あとから読みたい。したがって**差分は計算結果を保存する**ことになる。

保存するとき、`{ kind: 'field.added', table: 'deal', field: 'competitor' }` のような
**機械キーだけを保存すると、あとで読めなくなる**。読む時点の定義でラベルを引き直すことになり、

- そのフィールドがさらに改名されたら、当時の言葉ではなくなる
- 見送りになって定義から消えたら、**何も表示できなくなる**

これは新しい問題ではない。要望の対象（`definitionRef`）は逆に**機械キーで保存して
表示時に解決する**設計にしてある（phase-9 決定A）。違いは時制で、対象は「いまの定義の
どこを指しているか」なので解決できないこと自体が情報になる（画面に「いまの定義に無い」と出る）。
一方**差分は「そのときの定義がどうだったか」の記録**なので、解決を後回しにできない。

→ **`BundleDiff` のエントリは、計算時にラベルを解決した文字列を持つ**（機械キーは併記する）。

### 2-2. 前後の2枚を並べて描くと、変わっていないものまで動く（phase-9 論点F）

遷移グラフを「変更前」「変更後」の2枚で並べると、ノードを1つ足しただけで rank が変わり、
**関係ないノードまで全部動く**。人間は「動いたもの」を「変わったもの」と読むので、
何が変わったのか分からなくなる。

→ **合併グラフを1枚描く**。ノード集合は旧 ∪ 新、**rank は新側の定義で計算**し、
削除されたノードは「前任者の rank + 1」を借りる。残るノードの位置は動かない。

### 2-3. 影響件数には、適用前には数えられないものがある

出口条件は SQL に変換できる範囲に限られている（§8-1）ので、**新しい定義の条件式を
いまのデータに対して評価できる**。これは kintone に原理的にできないことで、
`alt plan` が「DB に何が起きるか」を出すのに対して「**業務に何が起きるか**」を出す。

ただし2つ、実装で必ず踏む穴がある。

⚠ **新しい条件が新しいフィールドを見ていたら、適用前には数えられない。**
「競合他社を足して、それを見る出口条件も足す」という変更では、条件式が参照する列が
DB にまだ無い。素直に SQL を投げると `no such column` で落ちる。
→ `referencedFields()` で参照先を洗い、**適用済みバンドルに無いフィールドを見ている条件は
数えずに「新しい項目を見ているので、適用前には数えられない」と出す**。

⚠ **`NOT (条件)` で未充足を数えてはいけない。** SQL の比較は NULL を伝播するので、
`initial_billing` が NULL のとき `> 0` は偽ではなく NULL になり、`NOT` を通しても真にならない。
サーバの評価が `=== 1` で見ている（`exit-checks.ts` の注記）のと同じ罠。
→ **「そのステップにいる件数」と「条件を満たす件数」を別々に数えて引く**。
`countRecords()` を2回呼ぶだけで、新しい SQL は要らない。

## 3. 論点と推奨（着手時に決めるもの）

### 論点A: 比べる2つのバンドルをどこから取るか

| 案 | 評価 |
|---|---|
| **1. 適用済み JSON vs 作業ツリー**（推奨） | `before` = `data/definitions.json`（サーバが実際に読んでいるもの）、`after` = CLI の `loadBundle()`。**両方を持っているのは CLI だけ**。適用したら自動で「変更なし」になる |
| 2. FE が適用済みをサーバから取り、自分の import と比べる | FE の `@alt/definitions` はビルド時の作業ツリー。dev では動くが、本番ビルドでは常に一致するので**意味を持つのは開発機の上だけ**。適用後に消えるので保存にも使えない |
| 3. Git の2つの ref を比べる | Git 依存が CLI に入る。「適用済み ＝ main の HEAD」が保証されるのは CI 経由の運用が固まってから（§5-1） |

**推奨: 案1。** `alt diff [--applied <path>]`。既定は `data/definitions.json`。

### 論点B: 何を「意味のある単位」とするか

汎用 JSON diff にはしない（`fields.competitor.required: false → true` のような出力は
起票者にも開発者にも読めない）。v1 で見るものを列挙する:

| 対象 | 見る変化 |
|---|---|
| テーブル | 追加 / 削除 / 表示名 |
| フィールド | 追加 / 削除 / 型 / 表示名 / 必須 / 参照先（`references`・`definitionRef`）/ enum 候補の増減と改名 |
| ロール | 追加 / 削除 / 表示名 |
| フロー | 追加 / 削除 / 表示名 / ゴール / 見る人（`viewers`） |
| ステップ | 追加 / 削除 / 表示名 / 意図（`intent`）/ 担当ロール / 遷移先（`next`）の増減 |
| 出口条件 | 追加 / 削除 / 種類（自動↔手動）/ 表示名 / 充足のしかた（`howTo`）/ **条件式が変わった**（中身の差は出さず「見ているデータ」の増減を添える） |
| バインディング | 追加 / 削除 / 位置づけ（`role`）/ 目的（`purpose`）/ 行レベル条件が変わった |

**見ないもの**: `reads` / `writes` の変化（バインディングの access に導出されて現れる）、
条件式 AST の構造そのものの差（「変わった」＋ `referencedFields` の増減で足りる）。

### 論点C: 業務の言葉をどこで解決するか

§2-1 のとおり**計算時に解決する**。問題は「その日本語をどこに書くか」。

| 案 | 評価 |
|---|---|
| **1. `@alt/diff` が整形済みの文字列を持つ**（推奨） | 保存した提案があとで読める。CLI と FE で文言が食い違わない。**欠点: パッケージに UI の文言が入る** — 客先1社・日本語のみなので許容する |
| 2. エントリは構造のみ、文言は各表示側 | パッケージは綺麗だが、CLI と FE で二重に書くことになり、**保存した JSON は表示側の版に依存する**（§2-1 が崩れる） |

**推奨: 案1。** ただし `where`（場所）と `summary`（1行）を分けて持ち、
表示側が並べ方（木にする・グルーピング）を決められるようにする。

### 論点D: 合併グラフをどこで計算するか（= `layoutFlow` の置き場）

合併グラフは**保存される**（§2-1）ので、rank・row まで含めて計算済みで持つ必要がある。
計算するのは CLI 側（`alt diff`）なので、`layoutFlow()` がパッケージから見えないといけない。
いまは `apps/main/src/flows/flowGraph.ts` にある。

| 案 | 評価 |
|---|---|
| **1. `layoutFlow` を `@alt/dsl` へ移す**（推奨） | `usedTables()` / `referencedFields()` / `definitionRefOptions()` と同じ「**定義に対する純関数**」の棚。**SVG の座標計算は FE のまま**（phase-5 の分け方を保つ）。移動は1ファイル + テスト + import 1行 |
| 2. `@alt/diff` に置く | FE の参照画面（差分と無関係）が diff パッケージから import することになり、名前がねじれる |
| 3. FE に残し、提案には前後の `FlowDef` を丸ごと保存して FE が計算 | 移動が要らない。ただし保存 JSON が重くなり、**同じアルゴリズムの置き場が FE 固定**になる（`alt diff` のテキスト出力からグラフを出す道が閉じる） |

**推奨: 案1。** ⚠ `@alt/dsl` に置くが**Go 契約の外**（`referencedFields` と同じ扱い）。
移動時に挙動は1つも変えない — フェーズ5 のテストがそのまま通ることを移設の条件にする。

### 論点E: 差分をどうやって要望に紐づけるか（完了条件5）

| 案 | 評価 |
|---|---|
| **1. `change_request` に `proposal: json('変更案')` を足し、`alt diff --request <id>` が書く**（推奨） | 保存されるので適用後も残る。書くのは対応者（＝開発者＝`admin`、phase-9 決定J）で、**作業ツリーと DB の両方を持っているのは CLI だけ**。phase-9 論点G の推奨（「CLI 側で計算し、結果を要望レコードに書く」）そのまま |
| 2. やりとり（`change_request_message`）にテキストで書く | 列を足さずに済むが、グラフも件数も持てず、機械で読み直せない |
| 3. サーバが提案バンドルを読んで API で返す | サーバに「適用済みでない定義」を持たせることになる。定義レジストリが2枚になるのは、いちばん壊しやすい場所を壊す |

**推奨: 案1。** 書き込みは `closeCurrentRow` + `insertRecord`（`alt seed` と同じ経路）で、
**`ChangeContext` に `changedFlow: 'request'` を載せる** — プラットフォームの履歴に
「どの業務のどの段階で変わったか」が残る（§4-1 の配当がここでも効く）。

⚠ これは `alt seed` に続く**2つめの「API を通らない書き込み」**になる（§8-2 論点7）。
`seed` と違い業務データを書くので、着手時に §8-2 へ追記する。

### 論点F: 影響件数はどこまで数えるか（完了条件4）

phase-9 論点G は「v1 は新しい出口条件の未充足件数1種類に絞る」を推奨していた。
実装してみると**どれも `countRecords()` 1〜2本**で、分岐するのは「何を数えるか」だけなので、
安いものは足す。

| # | 数えるもの | 実装 | 判断 |
|---|---|---|---|
| 1 | **追加された自動判定の未充足件数** | そのステップにいる件数 − 条件を満たす件数（§2-3） | **必須**（完了条件4） |
| 2 | **消えるステップに滞留している件数** | `countRecords({flow, steps:[key]})` 1本 | **入れる**。「行き先が無くなる」は業務が止まる変更で、いちばん見せる価値がある |
| 3 | **必須になるフィールドが空の件数** | `countRecords({where: isNull})` 1本 | **入れる**。既存レコードが以後 PATCH できなくなる |

**推奨: 3種類。** どれも「数えられなければ理由を出す」（§2-3 の ⚠）を共通の作りにする。

### 論点G: フィールドの順序（§8-2 論点18）を今解くか

要求には「増減・**移動**が分かる」とある。移動を出すには定義が順序を持つ必要がある。

**推奨: 解かない。** 理由は波及の広さではなく、**出しても嘘になる**から:

- 画面の並びは `DealForm.tsx` / `RequestNew.tsx` の**JSX の手書き順**で、定義の順序は
  画面に効いていない。「項目が移動しました」と出しても、実際には何も動かない
- 定義の順序が意味を持つのは「フォームを定義から描く」ようになったときで、
  そのとき `fields` を配列にするか順序を別に持つかを**画面と一緒に**決めればよい

※ 安い折衷（`table()` が宣言順を `fieldOrder: string[]` として焼き込む）は存在するが、
上の理由で**いま入れると「定義に順序がある」という嘘が1つ増える**ので採らない。
§8-2 論点18 は開いたまま残す。

### 論点H: `alt diff` という名前

§4-4 には `alt diff --since-generated`（FE を生成した時点からの定義差分 → AI が FE に反映する）
という別物が予告されている。**軸が違う**:

| | 比べるもの | 何のため |
|---|---|---|
| 今回の `alt diff` | 適用済み ↔ 作業ツリー | **業務に何が起きるかを人に見せる** |
| §4-4 の `--since-generated` | FE 生成時点 ↔ いま | **FE のコードを追随させる** |

**推奨: 今回は `alt diff` を素の名前で取る。** `--since-generated` を作るときは
比較元を指すオプション（`--applied` と同じ枠）として足せばよく、いま名前を予約しない。

## 4. 形

### 4-1. パッケージ `@alt/diff`（新規）

依存は `@alt/dsl` だけ。CLI と FE の両方が使う（どちらも TypeScript のまま残る側なので、
`@alt/server` と違い**捨てる前提のコードではない**）。

```ts
/** 意味のある単位の差分。ラベルは解決済み（§2-1）。 */
export function diffBundles(before: DefinitionBundle, after: DefinitionBundle): BundleDiff

/** 合併グラフ1枚（§2-2）。rank は after 側で計算し、消えたノードは前任者+1 を借りる。 */
export function mergeFlowGraph(before: FlowDef | undefined, after: FlowDef | undefined): MergedGraph
```

### 4-2. `BundleDiff` の形

```ts
export type ChangeKind = 'added' | 'removed' | 'changed'

export interface DiffEntry {
  /** 機械が分岐するためのキー。'field.added' / 'step.exit.added' など */
  kind: string
  change: ChangeKind
  /** 業務の言葉での場所。['営業（新規開拓）', '提案'] — 表示側はこれで木にする */
  where: string[]
  /** 業務の言葉で1行。「出る条件が1つ増える: 見積を提示した（自動判定）」 */
  summary: string
  /** 補足。howTo・前後の値・見ているデータの増減 */
  detail?: string
  /** 開発者向けの機械キー。'sales.proposed.timing_confirmed'。FE は出さない */
  ref?: string
}

export interface MergedGraph {
  flowKey: string
  flowName: string
  nodes: Array<GraphNode & { change: ChangeKind | 'unchanged' }>
  edges: Array<GraphEdge & { change: ChangeKind | 'unchanged' }>
}

export interface Impact {
  /** 対応する DiffEntry.ref */
  ref: string
  where: string[]
  /** 「新しい条件が未充足になる案件: 87 件（提案にいる 214 件のうち）」 */
  summary: string
  count: number
  total: number
}

export interface BundleDiff {
  entries: DiffEntry[]
  /** 変わったフローの合併グラフだけ */
  graphs: MergedGraph[]
  /** CLI が DB を見て埋める。数えていなければ空 */
  impacts: Impact[]
  /** 数えられなかったもの（理由つき。§2-3） */
  notCounted: Array<{ ref: string; reason: string }>
  empty: boolean
}
```

⚠ **これが要望レコードに保存される形**でもある（論点E）。だから
`GraphNode`（rank・row を含む）まで計算済みで入っている。

### 4-3. `alt diff` の使い方

```
alt diff [--applied <path>] [--db <path>] [--request <id>] [--no-impact] [--json]
    適用済みの定義と作業ツリーの定義を比べる
    --applied  比較元（既定: data/definitions.json）
    --request  差分を「変更案」として要望レコードに書き込む
    --db       影響件数の集計先・--request の書き込み先（apply と同じ解決）
    --no-impact  DB を見ない（差分だけ）
```

**差分があっても終了コードは 0**（`validate` と違い、これは検査ではなく説明）。
既定の出力は開発者向け（機械キーつき）、`--json` は `BundleDiff` そのまま。

### 4-4. FE

- 要望詳細（`RequestDetail.tsx`）に「**この要望で変わること**」セクションを足す。
  `record.proposal` があるときだけ出す。`where` でグループ化して phase-9 論点E の絵にする
- 合併グラフは `GraphSvg` を `FlowReference.tsx` から**そのまま切り出して**共有する。
  `change` に応じて class を足すだけで、レイアウトのコードは1つに保つ
  （追加 = 実線＋強調 / 削除 = 点線＋取り消し / 変更 = 枠を変える）
- 影響件数は差分の下に。「いま入っている案件への影響」

⚠ **一覧やフォームには手を入れない**（§4-3「一覧とフォームは各フローの手書きのまま」）。

## 9. 動作確認の手順

⚠ **順番が意味を持つ。** 「適用済み」を先に確定させてから作業ツリーを変える。

```sh
# 1. 基準を作る（適用済み = 作業ツリー）
docker compose exec dev pnpm alt apply --recreate
docker compose exec dev pnpm alt export --out data/definitions.json
docker compose exec dev pnpm alt seed --reset --deals 10000
docker compose exec -d dev pnpm serve
docker compose exec -d dev pnpm dev

docker compose exec dev pnpm alt diff      # → 「変更なし」（完了条件6の前半）

# 2. 起票者（山田）が要望を出す（画面から）
# 3. 作業ツリーの定義を変える（デモ用の一時変更）
#    - deal に「競合他社」を足す
#    - 提案ステップに出口条件を1つ足す（既存フィールドを見るもの＝件数が数えられる）
docker compose exec dev pnpm alt diff                    # 開発者向けテキスト + 影響件数
docker compose exec dev pnpm alt diff --request <要望ID>  # 要望に添える

# 4. 山田で要望詳細を開く → 「この要望で変わること」が業務の言葉で読める
# 5. デモ用の一時変更を revert する
#    → alt diff は「変更なし」に戻るが、**要望に添えた変更案は残って読める**（完了条件6）
```

⚠ 定義を足したら**サーバを上げ直す**（`data/definitions.json` は起動時に1回読む。phase-9 §7-7）。

## 11. 実装中に決めたこと・見つけたもの

| # | 決定 / 発見 | 理由 |
|---|---|---|
| **H** | **「数えられません」の理由も業務の言葉で出す** | 動作確認で `新しい項目（deal.competitorUnknown）を見ているので…` が**起票者の画面に出ていた**（完了条件2 違反）。原因は理由の文だけ「解決できない ＝ ラベルが引けない」で機械名に落ちていたこと。**引き先を変更後の定義にすれば引ける**（解決できないのは適用済み側であって、新しい定義には当然ある）。→ 「新しい項目「案件.更新メモ」を見ているので…」。⚠ **業務の言葉で出す約束は、正常系だけでなく「できませんでした」の側にも要る** |
| **I** | **合併グラフの位置は `next` の前任者ではなく「旧レイアウトでの並び」から借りる** | 最初は「そのノードへ入ってきていたステップの rank + 1」にしたが、**差し戻し（後退辺）で入ってくる相手が「前任者」に混ざる**。a→b→c で c→b の差し戻しがあると、消えた b が c の右（rank 2）に飛ぶ。`layoutFlow(before)` の rank を基準にして「自分より左にいて、いまも残っているノードのいちばん右 + 1」にした |
| **J** | **エントリの順は「まず何が増えたか」** | 段階の増減を先に、その中の変更を後に出す2パスにした。宣言順のまま出すと、増えた段階の話が「提案の進み先が変わります」の下に埋もれる |
| **K** | **`countRecords` の列名は `total`**（`count` ではない） | 影響件数がすべて 0 で出た。`COUNT(*) AS "total"` を `.count` で読んでいた。**0 件と「数えられていない」が見分けられない**という §2-3 の懸念が、実装のバグとして先に出た形 |
| **L** | **手動チェックの追加は影響として数えない** | 数えても「そのステップにいる全件が未確認」にしかならない（`_manual_check` に行が無いので当然）。情報量がゼロなので出さない |
| **M** | **`sameValue` は JSON 文字列の一致で済ませない** | 比べるのは「JSON から読んだバンドル」と「TS が組み立てたバンドル」で、**キーの順序が一致する保証がない**。順序差を差分として報告すると、何も直していないのに差分が出る。`undefined` と欠けたキーも同一視する（DSL のビルダーが「未指定ならキーごと持たない」形で書いているため） |

## 12. ここまで来て分かったこと

- **「業務に何が起きるか」が数字で出た。** 「この条件を足すと、いま提案にいる 2000 件が全部未充足になります」は
  kintone に原理的に出せない（設定変更の影響を事前に見る手段が無い）。`alt plan` の
  「DB に何が起きるか」に対する**業務側の対** で、§5-4 の差別化点がエンドユーザーに見える形になった
- **保存物としての差分は、正常系より「できませんでした」の言葉づかいで破れる**（決定H）。
  業務の言葉で出す約束は、成功したときの文だけを見ていると守れていないことに気づけない
- **フェーズ5 の投資が3回目の配当を出した。** ラベル・`intent`・`howTo`・`referencedFields` が
  無ければ、この差分は型名と列名の羅列にしかならなかった。「定義が業務の言葉を持つ」は
  参照画面（フェーズ5）・要望の対象表示（フェーズ9）に続いてここでも効いている
- **`layoutFlow` の移設は、置き場所を1つ動かしただけで新しい絵が1枚増えた**（決定C）。
  `mergeFlowGraph` が書けたのは、レイアウトが純関数だったから
- §8-2 に**新しい論点を1件**足す: CLI が業務データを書く2例目（論点7）
