## 0. 要求

`apps/main` のデータ取得を TanStack Query に移し、**手書きの並行制御を消す**。

- 動機は §8-2 論点20 に書いたとおり1つだけ — **取得ライブラリが持っている機能を
  手で書き直している箇所が5種類ある**こと。壊れてはいない（フェーズ7・9 の実機欠陥は
  どちらも取得が原因ではない）し、社内・低トラフィックなので通信量も動機にならない
- **適期が来た**。フェーズ11 でポーリングが3本目になり、次に画面が増えるフロー
  （制作・MEO運用）の手前がいちばん効く、と論点20 自身が言っている。次のフェーズで
  画面を足すたびに `let live` を書き写すか、いま消すか
- **サーバは変えない**。`packages/*` に差分が出たらこのフェーズのスコープ違反
- **挙動も変えない**。決定K（ソフト/ハード世代）・決定N（前ユーザーの未読を残さない）・
  決定R/S（グリッドのフォーカスと編集不可の理由）・フェーズ11 のチャット追随は
  すべてそのまま。変わってよいのは §9 に列挙した2つの改善方向の差分だけ

## 1. 現状 — 何が手書きか（2026-08-10 実測）

取得を投げる場所は **9ファイル**（8画面 + `useDealPage`）。論点20 の棚卸し
（フェーズ11 前 = 7ファイル + token）から `DealChat` が増えている。

| # | 手書きしているもの | 場所 |

  知らず、`DealChat` は `RequestChat` の配線を踏襲しただけ。だから移行で書き直すのは

## 2. 前提の解説

### 2-1. 何が何に置き換わるか

| 手書き | TanStack Query | 補足 |
|---|---|---|
| ① `live` / `token` | **queryKey の同一性**。キーが変われば前の取得は別のクエリで、遅れて返っても現在のキーのデータに混ざらない | 各 effect の破棄処理が丸ごと消える |
| ② `requested` Set | **同一キーの in-flight 共有**（自動 dedup） | StrictMode の二重実行も同じ仕組みで無害化 |
| ③ `setInterval` | **`refetchInterval`** | クリーンアップ・`live` ガードごと消える |
| ④ `generation` | **`invalidateQueries`** | 「書いたら読み直す」が宣言でなく命令1回になる |
| ⑤ `replaceRow` | **`setQueryData`**（グリッドは `setQueriesData`） | PATCH レスポンスでその場を置換、は同じ |

### 2-2. ライブラリを入れても消えないもの（論点20 の予告どおり）

- **決定K（ソフト/ハード世代）はキー設計として残る**。ハード世代 = filters / sort /
  asOf / user がキーの一部で、変われば別クエリ。ソフト世代 = snapshot を取り直す
  カウンタをキーに含める。ライブラリは区別を肩代わりしない
- **一覧グリッドは suspend させられない**。未取得インデックスにスケルトン行を出すのが
  仕様（行の高さを保ってスクロール位置を守る）。窓のクエリは `staleTime: Infinity`
  （同じ snapshot の同じ窓は不変なので、再取得の理由が無い）
- **キーには `flow` を必ず含める**（論点20 の ⚠）。API クライアントは業務フローごとに
  1本（決定14）で、同じテーブルでもフローが違えば認可の範囲が違う（現に `employee` は
  request、`company` は sales から引いている）。`as_of` も `user`（詐称）も同じ理由で
  キーに入る — 今日の各 effect の依存配列に並んでいるものが、そのままキーになる
- **書き込みの `busy` / `onError`**: mutation は取得ではない。手を入れない（論点A）

## 3. 論点と推奨

### 論点A: スコープの線 — 取得だけ移す。書き込みは動かさない

論点20 が数えた5種類は全部「取得」の話。書き込み（`mutate` の busy 管理・
`.catch(onError)`・チャット投稿の下書き保持）は手書きでも二重実装になっていない。

**推奨: 書き込みは `useMutation` に移さない。** 触るのはキャッシュに触れる2点だけ —
④（投稿成功 → `invalidateQueries`）と ⑤（PATCH レスポンス → `setQueryData`）。
`useMutation` は isPending 相当をくれるが、いまの `busy` state で足りており、
移すと差分が倍になる。必要になったら後から足せる（付加的）。

### 論点B: エラーの構造 — Suspense / ErrorBoundary は入れない（論点20 の記述からの変更）

論点20 は「Suspense を併せると `T[] | undefined` の分岐と `onError` の配りが
ErrorBoundary に構造として移る」と書いた。計画で突き合わせた結果、**このフェーズでは
入れない**ことを推奨する。理由:

- **fetch エラーの配りは Suspense 無しで消える**。TanStack v5 は `useQuery` から
  `onError` コールバックを廃止した代わりに、**`QueryCache` の `onError`（全クエリ共通の
  1箇所）** がある。QueryClient を App が作り、そこで今のバナー（`setError`）に流せば、
  **全画面の fetch 用 `onError` 配りが1行に畳まれる**。今日の「どの画面のエラーも
  上部バナー1本」という UX がそのまま保たれる
  - ⚠ **そのために App を2層に割る**（レビュー①）。`useQuery` は**自分が描いた
    Provider を見られない**（コンテキストは自分より上を探す）ので、
    「App が Provider を張る」と「App がマスタをクエリで引く」は同じ関数では両立しない。
    外側の `App` が `error` state と QueryClient を持って Provider を張り、
    中身（ヘッダ・ナビ・マスタ・ルーティング）は `AppBody` に移す。
    移動は JSX が主で、ロジックの変更は入らない。
    `setError` は `useState` のセッタなので同一性が安定していて、
    QueryClient の生成時に閉じ込めて問題ない
- ErrorBoundary に移すと**チャットとグリッドで今日より悪くなる**。チャットの取得失敗は
  今日「バナーが出るが詳細画面は生きている」。boundary に投げると区画ではなく
  ルート全体が倒れる。例外を書き分けるくらいなら、境界を入れない方が構造が単純
- `T[] | undefined → 読み込み中` の分岐は**並行制御ではなく描画**。残しても論点20 の
  動機（手書きの並行制御を消す）は完遂する

エラーを握りつぶす3箇所は意図的なので保つ: `UnreadBadge`（数えられないことは業務の
失敗ではない → クエリの `meta.silent` を立てて共通 `onError` が黙る）、App の会社マスタ
（非参加者は読めなくて正しい → queryFn 内で catch して `[]`）、`RequestNew` の対象
レコード（読めなくても起票は妨げない → 同上）。

「画面を移ったらエラーを消す」effect（App）は**残す**。mutation エラーのバナーにも
効いている必要があるため。Suspense / ErrorBoundary は §5 の「作らないもの」へ
（再訪条件: 画面が増えて `undefined` 分岐が負担として実感されたら。付加的に足せる）。

### 論点C: queryKey の規約 — 認可の文脈を先頭に固定する

**キーは `[flow, table, user, asOf, ...固有]` の順で機械的に作る。** 規約はコメントでなく
コードにする — `shell/query.ts`（新設）にキー生成ヘルパを置き、画面は配列リテラルを
手書きしない。

- `flow` が先頭: 決定14 の帰結。取り違えると「別フローの認可範囲のキャッシュを読む」
  になる — 指定漏れを構造的に不可能にする
  - ⚠ **`flow` はヘルパの引数ではなく `Client` から読む**（レビュー②）。文字列で渡す形だと
    「`client` は `clients.request` なのにキーは `'sales'`」が**書けてしまい**、
    規約がレビュー頼みに戻る。`createClient(auth, flow)` はもともと flow を閉じ込めて
    いるので、`Client` に `readonly flow: string` を1つ生やして
    `keyOf(client, table, …)` が `client.flow` を読む。取り違えが型で不可能になり、
    画面が書くのは「どのクライアントで引くか」1回だけになる（＝決定14 そのもの）
- `user` を含める: 詐称切替はヘッダしか変えないが、`_permissions` も rowFilter も変わる。
  キーに入れれば「切替後に前ユーザーのキャッシュが見える」が原理的に起きない
  （決定N をキーの同一性で保証し直す形。切替時のリセット effect は不要になる）
- `asOf` を含める: 時点が違えば別のデータ

### 論点D: グリッド（`useDealPage`）— インターフェースを固定して内部だけ差し替える

最難関はここ。窓取得・snapshot 固定・2種類の世代・置換・スケルトンが1つの hook に
集約されている。ただし**外側はすでに正しい形**をしている — `DealPage`
（`resetKey` / `total` / `rowAt` / `ensureRange` / `replaceRow` / `refresh`）は
取得の実装を一切漏らしておらず、`DealList.tsx` と browser テスト6本はこの
インターフェースしか見ていない。

**推奨: `DealPage` の型を1文字も変えず、`useDealPage` の内部だけを置き換える。**

- **頭クエリ**（ハード世代の起点）: キー `[sales, deal, user, asOf, filters, sort, softGen]`。
  anchor ページを snapshot 無しで引き、返った `now` / `total` / 行を持つ。
  ソフト世代（`refresh()`）は `softGen` カウンタを進めるだけ = 決定K がキーに写る
- **窓クエリ**: キーに `snapshot` とページ番号を足し、`useQueries` で「見えている範囲から
  導出したページ集合」を宣言する。`staleTime: Infinity`（同 snapshot の同じ窓は不変）。
  `requested` Set は同一キーの dedup がそのまま代替する
- **行の蓄積 Map は今日のまま残す**（レビュー③）。当初は「ソフト世代のフォールバック」
  と書いていたが、**用途は2つあって機構は1つで足りる**:
  1. ソフト世代（確定しても白くならない）— 新しい `snapshot` で窓が来るまで前の行を出す
  2. **スクロールで通り過ぎた窓** — 宣言するページ集合を可視範囲に絞ると、
     virtualizer の overscan が範囲外を描いた瞬間に `rowAt` が `undefined` を返して
     スケルトンに戻る。今日の `rows` Map は世代の間ずっと全部持っている
  つまり「窓クエリの結果を絶対インデックスの Map に流し込む」という今日の `indexed`
  をそのまま残し、`rowAt` はそこを読む。ここだけ手書きが残るのは、ライブラリが
  キーをまたぐ蓄積を持たないため（`placeholderData` はキー単位）。**理由をコードに書く**
- ⑤ `replaceRow`: 現世代の窓クエリ群に `setQueriesData`、フォールバック ref も置換
- **順序は最後**（§7）。他の8画面と共通配線が全部通ってから着手する。
  **退路**: browser テストか手動確認で決定K/R/S の再現に詰まったら、`useDealPage` は
  手書きのまま残して完了にする（①②の残置1ファイルを §8-2 論点20 の残件として記録）。
  外側を固定してあるから、後日単独でやり直せる

### 論点E: 重複取得 — 強制共有はしない

`UnreadBadge`（全件×3テーブル）と要望一覧・要望チャット（同じテーブルを別条件）の
重複は、キーが違うので移行しても自動では消えない。消すには「チャットも全件で引いて
FE で絞る」ようにパラメータを寄せる必要がある。

**推奨: 寄せない。** キーは「サーバに投げるパラメータそのもの」から機械的に決め、
共有はキーが一致した場合の自然な帰結に限る。理由: 動機は手書きの並行制御を消すこと
だけで、通信量ではない（論点20 本文）。取得の形を画面の都合で歪めて共有させるのは、
データ層で「共通部品に寄せる」（§4-3 が禁じた構造）をやることになる。
`MASTER_LIMIT` の意味も変わってしまう（全件500件打ち切りの網が別の画面に波及する）。

### 論点F: 既定値 — 「今日と同じ挙動」を既定にする

TanStack の既定は今日の挙動と3箇所ずれる。`shell/query.ts` の QueryClient 生成で
今日側に倒す:

| 既定 | 今日 | 設定 |
|---|---|---|
| 失敗を3回リトライ | リトライしない（エラーは即バナー） | `retry: false` |
| ウィンドウフォーカスで再取得 | しない | `refetchOnWindowFocus: false` |
| `placeholderData` なし | なし | 既定のまま。**未読バッジには絶対に足さない**（決定N: 前ユーザー・前の数を一瞬も見せない）。マスタ（App）だけ `placeholderData: (prev) => prev` を検討 — 今日もユーザー切替中は前のマスタ表示が残る挙動なので、こちらは付けるほうが今日と同じ |

`staleTime` は既定 0 のまま（再マウントで取り直す = 今日と同じ鮮度）。グリッドの
窓クエリだけ `Infinity` を明示（論点D）。

### 論点G: 依存 — `@tanstack/react-query` v5 のみ。devtools は入れない

- `@tanstack/react-virtual` と同系列（論点20 が SWR でなくこちらを選んだ理由）。
  React 19 対応は v5 系。正確な版は着手時に pnpm が解決したものを記録する
- ワークスペースパッケージではないので「4箇所」の追記は不要（`check:wiring` の対象外）。
  `package.json` を編集すれば hook が `pnpm install` を流す
- devtools（`@tanstack/react-query-devtools`）は入れない。UI を持つ依存を足す理由が
  いま無い。困ってから

## 4. 決定事項（2026-08-10 レビューで確定）

| 論点 | 判断 | 帰結 |
|---|---|---|
| A スコープ | **取得だけ移す**。書き込みは `busy` state のまま、キャッシュに触れる2点（invalidate / setQueryData）だけ足す | 差分が「effect の置き換え」に閉じる |
| B エラー | **Suspense / ErrorBoundary は入れない**。fetch エラーは `QueryCache.onError` 1本で今のバナーへ。意図的な握りつぶし3箇所は `meta.silent` / queryFn 内 catch で保つ。**そのため App を2層に割る**（レビュー①） | `onError` prop は mutation 専用に痩せる。画面またぎのエラー消去 effect は残る |
| C キー規約 | `[flow, table, user, asOf, ...固有]`。`shell/query.ts` のヘルパで生成し手書きさせない。**`flow` は `Client.flow` から読む**（レビュー②） | 認可の文脈の取り違えが**型で**起きない。詐称切替のリセットがキー同一性の保証になる |
| D グリッド | `DealPage` インターフェース固定・内部だけ差し替え・**最後に着手・退路あり**。**行の蓄積 Map は残す**（レビュー③） | `DealList.tsx` と browser テストは無傷。詰まったら残置して完了できる |
| E 重複取得 | 強制共有しない。キーはパラメータから機械的に | データ層の「共通部品化」を避ける。重複は残るが各々が宣言になる |
| F 既定値 | `retry: false` / `refetchOnWindowFocus: false` / placeholder は原則なし | 「ライブラリを入れたら挙動が変わった」を潰す |
| G 依存 | `@tanstack/react-query` v5 のみ | シェルの決定（Provider とキー規約がアプリ全体の構造を決める）。§4-3「共通化はシェルのみ」の範囲内 |

## 5. スコープに入れないもの

- **Suspense / ErrorBoundary**（論点B。再訪条件: 画面が増えて `undefined` 分岐が負担に
  なったら。付加的に足せる）
- **`useMutation` への移行**（論点A。同上）
- **重複取得の解消**（論点E。動機が通信量になったら = ならない見込み）
- **未読バッジの数え方の変更**（全件取得×FE 突き合わせのまま。フェーズ9 決定の制約が
  そのまま残る — 要望が数百件を超えたら数え方ごと考え直す、は変わらない）
- devtools・キャッシュの永続化・offline 対応
- サーバ側の変更一切

## 6. この計画が置いている前提

- `shell/chat/ChatPanel` は props（`messages` / `onPost` …）しか見ていないので無傷。
  フェーズ11 の追随・「新着 n 件 ↓」・IME ガードは部品側の実装で、取得の載せ替えの
  影響を受けない（`ChatPanel.browser.test` が動かぬ証拠になる）
- `shell/api.ts` は無傷。queryFn が今の `Client` を呼ぶだけで、api.ts は react-query を
  知らない（認証注入の設計もそのまま）
- `markRead`（要望詳細を開いたら既読）は**書き込み**なので effect のまま残る。
  ⚠ ここで未読バッジのクエリを `invalidateQueries` したくなるが、**やらない** —
  今日は次の 10 秒 tick でバッジが消える挙動で、即時化は改善であって移行ではない
  （§0「挙動も変えない」）。欲しくなったら1行で足せる
- structural sharing（内容が同じなら参照を保つ）により、ポーリングの空振りが
  再レンダーを起こさなくなる。挙動としては今日より静かになる方向のみ

## 7. タスク（依存順）— 2段階

**段階1: シェルと8画面**

## 9. 壊れうるもの・受け入れる挙動差

**壊れうるもの（＝完了条件で守るもの）**:

- 決定K/R/S（グリッド）— `DealList.browser.test` 6本 + §8-1 の手動確認
- 決定N（バッジ）— キーの同一性で保証し直す。placeholder を誤って付けると即死する
- フェーズ11 のチャット挙動 — 部品は無傷なので、壊れるとしたら配線（キー・interval）
- StrictMode の二重実行 — TanStack 側が想定済み（むしろ手書きより安全）

**受け入れる挙動差（改善方向のみ。実装中に増えたらここに追記）**:

- **非アクティブタブでポーリングが止まる**（`refetchIntervalInBackground` 既定 false）。
  今日は裏タブでも打ち続けている。フォーカスが戻ると次の tick で追いつく
- **画面を戻ったとき、キャッシュが即出て裏で更新される**（今日は毎回「読み込み中…」の
  白紙から）。stale が見える時間は最大で再取得1回ぶん
- **窓1枚の取得に失敗しても自動では取り直さない**（実装中に判明）。今日は
  `requested` から消して「スクロールし直せば再挑戦」にしていたが、その経路は
  **失敗のたびに再描画 → 再要求のループになりうる**形でもあった。移行後は
  絞り込み・並び・時点を変えるか画面を出入りするまで再挑戦しない。
  一覧全体が読めない失敗（403 など）は起点の窓に出るので、こちらは今までどおり
  バナーに出て 0 件として畳まれる
- **マスタが2本のクエリに分かれた**（実装中の判断）。従業員は request フロー・会社は
  sales フローから引いており、**キーの先頭 `flow` が違う**ので1本にまとめると
  どちらかのフローで嘘のキーになる。結果、今日は `Promise.all` で揃ってから
  一度に表示していたのが、**先に返ったほうから埋まる**。どちらも未取得のうちは
  今日と同じく「—」なので、退化ではない

**検証中に引っかかったので書き残す（フェーズ12 とは無関係の既存挙動）**:

- **セルを直すと、その行が一覧の先頭へ飛ぶ**。一覧の既定の並びが「更新が新しい順」
  （`valid_from DESC`、フェーズ3から）なので、確定した行は正しく先頭へ移る。
  1万件で確認していると「行が入れ替わった＝取得が壊れた」に見えるが、そうではない。
  ⚠ **決定K の「下のセルへ移って次を直す」は壊れない** — 先頭へ移った行より
  **下のインデックスは動かない**（ずれるのは上の行だけ）ので、`index + 1` は
  さっきと同じ案件を指し続ける。並びを固定して確かめたいなら列見出しで並べ替える
