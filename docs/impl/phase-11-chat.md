## 1. 現状 — どこからの距離か

| いまあるもの | 事実 |
|---|---|
| やりとりのデータモデル | **ある**（フェーズ9）。`change_request_message`（requestId / authorEmployeeId / body / postedAt=`createdAt` / authorKind）。AI の口（`authorKind: 'ai'`）も空けてある |
| やりとりのUI | **ある。ただしコメント欄型**。`RequestChat.tsx` は一覧＋投稿フォームで、自分の投稿は色違い（`.message.mine`）になるだけ。左右振り分け・自動スクロール・Enter送信は無い。8秒ポーリング |
| 投稿と業務フローの接続 | **ある**。出口条件 `replied`（起票者以外の書き込みが1件でもあると充足）が投稿で動く。だから投稿後は要望本体を読み直す（`onPosted`） |
| 未読 | **ある（要望用のみ）**。`UnreadBadge`（シェル・10秒ポーリング）。**全件（limit 500）を取ってFEで突き合わせ**る実装で、「数百件を超えたら数え方ごと考え直す」と実装自身に書いてある |
| 既読の記録 | **ある**。`change_request_read` ＋ `RequestDetail` の `markRead`。⚠ **readAt をクライアント時計で書いている**（`RequestDetail.tsx` の `new Date()`）。「クライアント時計を信用しない」（フェーズ6 決定A）との緊張が既にある |
| 案件側のチャット | **無い**。`DealDetail` はフロー面 → 内容 → 活動の縦積み |
| 追記型サブレコードの前例 | **2つ**。`activity`（業務イベント）と `change_request_message`（やりとり） |
| IME ガード | **ある**。`isImeKey`（`isComposing` / `keyCode 229`、フェーズ7）。ただし置き場は `flows/sales/cellEdit.ts` |
| browser テスト層 | **ある**（実 Chromium）。「DOMフォーカスの所在が本体」の挙動を書く場所 |
| 認可 | **viewer は書けない**。`requireOperator`（`authz.ts`）が create / update / advance の入口で止める。営業フローの参加は operator = `sales_rep`、viewer = `sales_manager`、**制作・MEO運用 = none（一覧ごと403）** |

**距離のまとめ**: (1) チャット風UIは**サーバも定義も触らない、FEだけの仕事**。
(2) 案件のチャットは**テーブル1本＋バインド**が本体で、基盤の変更は
「viewer が追記できるバインド宣言」の**1つだけ**（§4 決定A）。

## 2. 前提の解説

### 2-1. 「やりとり」は既にあり、足りないのは見た目と操作

データモデル・API・認可・ポーリング・未読バッジはフェーズ9で揃っている。
「チャット風にする」の中身は**表示と操作の変更**（吹き出し・自動スクロール・Enter送信）で、
サーバに1行も触らずにできる。逆に言うと、ここで新しい概念は増えない —
増えるのは (2) 側で、それも参加モデルの小さな拡張1つに畳んである。

### 2-2. 「案件のチャット」の隣には既に2つの前例がある

| | 何を記録するか | 誰が読むか |
|---|---|---|
| `activity`（活動） | **顧客との接触**（架電・訪問・商談。予定と実績） | **出口条件と KPI が読む**（アポ予定・決裁者に会えている） |
| `change_request_message` | 要望をめぐる**やりとり** | 人が読む。出口条件 `replied` も読む |

案件のチャットは**後者の2本目**であって、activity の代替や拡張ではない。
この区別が論点F（activity に混ぜない・記録の流出）の土台になる。

### 2-3. 要望チャットと案件チャットの決定的な差は「参加者」

要望フローは起票ステップの担当が全ロール（`ROLE_KEYS`）なので**全員が operator**。
だからフェーズ9では認可の問題が1つも出なかった。営業フローは違う:

| ロール | 営業フローへの参加 | チャットに書けるか（現状） |
|---|---|---|
| `sales_rep` | operator | 書ける |
| `sales_manager` | viewer（読み取り専用） | **書けない**（`requireOperator` が止める） |
| `production` / `meo_operator` | **none** | **読むことすらできない**（一覧ごと403） |
| `admin` | admin | 書ける |

案件チャットの主用途（担当↔マネージャーの相談、受注後の制作・運用への引き継ぎ）が
**参加モデルの壁にそのまま当たる**。ここが (2) の唯一の基盤論点で、§4 で決着させた。

## 3. 論点と推奨

### (1) やりとりのチャット風UI

#### 論点A: 「チャット風」の要素をどこまで入れるか

| 要素 | 引っかかり | 推奨 |
|---|---|---|
| 吹き出しの左右振り分け | なし。安い | 入れる |
| 高さ固定＋内部スクロール＋自動スクロール | **上を読んでいる最中にポーリング新着で飛ばさない**（最下部にいるときだけ追随。それ以外は「新着あり」の合図）。8秒ポーリングとの噛み合わせで一番壊れやすい | 入れる。browser テストで回帰化 |
| Enter送信（Shift+Enter で改行） | **IME 変換確定の Enter で誤送信**する罠。フェーズ7で解いた `isImeKey` の再利用先 | 入れる。ガード必須 |
| 日付区切り・連続投稿のまとめ | 表示だけ | 任意 |
| 未読線（ここから未読） | `readAt` から引けるが、(a) `markRead` が開いた瞬間に上書きするので**mark 前の値の保持**が要る、(b) その readAt は**クライアント時計**で書かれている（§1）。やるなら出どころごと直す | **v1 は見送り**（§8-2） |

#### 論点B: 左右の「自分」の軸

**meId（いま操作しているユーザー）が右、を採る。** 起票者/対応者の役割ベースにしない —
要望フローは全ロールが書けるので3人目が現れうるし、AI（`authorKind`）も将来ここに乗る。
役割ベースは2者前提が崩れた瞬間に破綻する。

#### 論点C: 編集・削除

チャット風にすると編集・削除の**期待が生まれる**。認可上は自分のメッセージの編集は既に
許されており（rowFilter が `authorEmployeeId = 自分`）、SCD2 で編集前も残るので安全。
削除 API はそもそも無い。**推奨: v1 は追記のみ（UIを作らない）**。期待が生まれることだけ
自覚しておく。

#### 論点D: 共通部品化 — 「実装中ずっと効く決定」13 の境界に触る

(2) をやるなら同じUIを2箇所で使う。決定13（フェーズ9 決定H）の境界は
「`_flow` を描くか、業務データを描くか」で、チャットは字義上は業務データ側 —
シェルに上げてはいけない側に見える。しかし実際に描くのは**形の決まった入力**
（誰が・いつ・本文・自分か）だけで、テーブル名もフィールド名も知らない。
kintone の失敗構造は「一覧とフォームが共通部品の表現力に縛られる」ことで、
メッセージ列の描画はそれに当たらない。

| 案 | 評価 |
|---|---|
| **D1. 表示部品だけ `shell/chat/` に置く**（推奨） | messages / meId / nameOf / onPost を受ける純表示。**取得・投稿・テーブル名・投稿後の読み直しは各フロー側に残す**（`replied` のような出口条件が動くかはフローの事情だから）。`StepTrack` と同じ「形の決まった入力を描く」側 |
| D2. コピーして2本 | フェーズ9 論点L1 で「コピーは3本目で必ず崩れる」とした同型 |
| D3. 定義に「会話」を第一級で持たせて自動で生やす | kintone のコメント欄の再現に近づく。**3本目が来るまでやらない** |

D1 を採ると決定13の言葉が「`_flow` を描くか」から
「**形が固定の機構を描くか、業務ごとの形（一覧・フォーム）を描くか**」に広がる。
基盤の言葉の変更なので、なし崩しにせず着手時に明示的に更新する（§8-1）。
`isImeKey` も sales 配下からシェルへ移す（部品が業務フローのコードを import する向きは逆）。

### (2) 案件詳細のチャット

#### 論点E: 何のためのチャットか（役割の定義）→ 決着済み（§4 決定B・C）

要望チャットには「内容の宣言性を詰める場」という役割の定義があった（フェーズ9 §2-2）。
案件チャットの役割は**案件をめぐる社内のやりとり（相談・指示・引き継ぎ）を、案件に紐づけて
残す場**と定義する。＝ kintone のレコードコメント欄の代替。顧客はこの系のユーザーでは
ないので、顧客とのやりとりは載らない（それは活動の記録）。

「誰と誰の会話か」が参加者スコープを決める。**引き継ぎを考慮する**（§0）ので、
相手は担当↔マネージャーに閉じず、**制作・MEO運用が入る** — won ステップの intent に
「ここで営業は終わり、制作・運用の工程へ引き継ぐ」と既に書いてあり、ドメインの実態が先にある。
帰結は §4 決定C（viewers への追加）。

#### 論点F: activity との境界（ドメインの罠）

チャットは activity と**別テーブルにする**。activity は出口条件（アポ予定・決裁者に会えている）
が読む**業務イベントの語彙**で、社内の相談が混入すると評価が汚れる。
「業務イベントはドメインモデルとして別に持つ」（§8-1）とも整合する。

本命のリスクは逆向きで、**チャットができると接触の報告がチャットに流れ、activity が
書かれなくなる**こと。そうなると自動判定が充足せず、「データを直すと勝手に充足に変わる」
という中核価値が痩せる。v1 でできる手当は**言葉の区別まで**
（チャット＝相談の場、活動＝顧客接点の記録）。チャットから活動を起こす導線は v2 の候補（§5）。

#### 論点G: データモデル

| 案 | 評価 |
|---|---|
| **G1. 業務テーブル `deal_message` を営業フローに primary バインド**（推奨） | `change_request_message` と**意図的に同じ形**（dealId / authorEmployeeId / body / postedAt=`createdAt` / authorKind。rowFilter は投稿者本人）。形を揃えること自体が将来の平台化（D3）の判断材料になる |
| G2. プラットフォーム `_comment`（全テーブルに生える） | フェーズ9 論点H 案2 の再訪条件は「業務テーブルで足りないと分かってから」。**2本目はまだ「足りない」ではなく「繰り返し」**。認可・API を手書きし直すコストも当時の評価のまま |

付記: **決着済み（won 等）の案件にも書ける。** `access` はステップの reads/writes の
**和**で導出され（`flow.ts` の `deriveUsage`）、行レベルの update は現在ステップに
縛られない（フェーズ9 論点J）。引き継ぎの会話は won の後に起きるので、これは付記ではなく
主用途の成立条件 — 追加の仕掛けなしで成立する。
v1 では deal_message を読む出口条件は作らない（チャットの存在を条件に使える配当はあるが、
営業フローの条件を変えるのは要望駆動でやる）。

#### 論点H: 認可 — viewer が書けない → 決着済み（§4 決定A）

| 案 | 評価 |
|---|---|
| **H1. バインドに「追記は参加者全員可」の宣言を1つ足す**（採用） | rowFilter と同じ置き場。参加の4種類と「入口で1回」を崩さず、viewer の一般定義も汚さない — このテーブルに限った「フローとテーブルの関係」の宣言として書く |
| H2. `sales_manager` をどこかのステップの roles に足して operator にする | 機構ゼロだが、フロー参照画面のステップカードに「担当: 営業、営業マネージャー」と**嘘が表示される**（定義が業務の教科書、という思想に反する）。advance や deal 編集は rowFilter で実害が出ないぶん、壊れるのが語彙だけなのが逆にたちが悪い |
| H3. 参加の種類に5つ目（commenter）を足す | 実例1つで型を増やさない。4値の単純さはフェーズ8の中核 |

#### 論点I: 未読 — 要望の実装は流用できない

要望の未読は「全件（limit 500）を取ってFEで突き合わせ」で、実装自身が「数百件を超えたら
数え方ごと考え直す」と書いている。**案件は1万件なので初日からその再訪条件を踏む**。
さらに `change_request_read` は SCD2 で「開くたびに版が積まれる」— 案件詳細は日に何十回も
開かれるので、既読テーブルの持ち方も再考が要る。

| 案 | 評価 |
|---|---|
| **I1. v1 は未読なしで出す**（推奨） | フェーズ9 論点H の「未読が無いとチャットは死ぬ」との緊張は認める。ただし未読は認可や履歴と違って**後付けできる**（read テーブルとバッジを足すだけ）ので、可逆な先送り。出すときに「返信に気づく手段が無い」と明記する |
| I2. 担当案件＋自分が書いた案件に絞ってサーバのフィルタで数える | 集計 API なしで可能だがクエリ設計が要る |
| I3. サーバに集計 API を足す | 「数える」需要の3例目（未確認件数・要望未読に次ぐ）なので筋はあるが、v1 でやる理由が無い |

引き継ぎ用途が入ると「気づかない」の業務影響が相談より大きい。ただし**引き継ぎの本体は
ステップ遷移（won に入ったこと）で、チャットは補足**。気づく仕組みはチャット未読ではなく
「won に入った案件」を制作が一覧フィルタで見る運用（URL 共有できる）に寄せられる。
**再訪条件: 引き継ぎの見落とし、または返信に気づけない実害が実際に起きたら**（→ I2 か I3）。

#### 論点J: 画面配置とポーリング

`DealDetail` は縦積み（フロー面 → 内容 → 活動）。開きっぱなしで眺める場なら2カラム化だが、
用があって開く場なら**活動の下に1区画で足りる**（v1 推奨）。ポーリングは `RequestChat` と
同じ「開いている間だけ8秒」。**過去表示（`as_of`）中は投稿フォームを畳む**
（サーバは ¬historical で守っているので、これは「書けない理由を先に見せる」決定Sの系譜）。
1万件グリッドには未読列などチャット関連を出さない。

## 4. 決定事項（2026-08-10 整理時）

| # | 決定 | 由来 | 理由 |
|---|---|---|---|
| **A** | **論点H は案H1**。バインドのオプション（rowFilter と同じ置き場）に「このテーブルへの**追記（create）は参加者全員可**」を宣言する。効く場所はサーバ `requireOperator` の分岐1箇所。開けるのは **create だけ** — update / advance は従来どおり viewer を止める（編集まで開けるかは編集UIを作るとき、論点C の再訪と一緒に決める）。「viewer は読むだけ」という文言（`authz.ts`・phase-8 文書・決定7）の更新とセット | 論点H | 参加の4種類と「入口で1回」を崩さない。フロー参照画面に嘘を出さない。宣言の名前は実装時に決める（§8-1） |
| **B** | **案件チャットの役割は「案件をめぐる社内のやりとり（相談・指示・引き継ぎ）を案件に紐づけて残す場」**。引き継ぎを含める | 論点E ＋ §0 の指示 | won の intent に「制作・運用の工程へ引き継ぐ」と既にあり、ドメインの実態が先にある。顧客接点の記録（activity）とは別物（論点F） |
| **C** | **営業フローの `viewers` に `production` と `meo_operator` を列挙で足す**（`sales_manager` と同じ形） | 決定B の帰結 | 引き継ぎの相手が現状 none（読めもしない）ではチャット以前に成立しない。**列挙にする**のは、viewers が「読む理由の明示」の場だから — マネージャーは「ヨミ会・予測のため」、制作・MEOは「引き継ぎ・運用のため」と理由が違う。導出（全ロール）にすると、将来足すロールが**判断なしに全案件を読めてしまう** |

決定C の波及（着手時に踏むもの）:

1. **制作・MEO運用は全案件（金額・確度含む）を読めるようになる**。「読みは全員」の原則の
   実現なので思想には合うが、見え方が変わる事実として押さえておく
2. **決着済み案件への書き込みが付記から主用途に昇格する**（論点G 付記のとおり、既に成立する）
3. **「403になるロール」の実例が営業フローから消える**。フェーズ8 の検証・テスト・文書で
   森（制作担当）が担っていた役の差し替えが要る
4. **将来、制作フロー・MEO運用フローが業務フローとして載ったとき**（domain-model.md の構想）、
   そのフローの target に別のチャットが生える。境界は「**案件の話は案件のチャット**」で、
   移行は不要 — 論点D の部品なら画面は安く増える

## 5. スコープに入れないもの

| 落とすもの | 理由 |
|---|---|
| メンション・通知（メール等） | 未読（論点I）の先の話。ヒアリングで依存度を見てから |
| 添付ファイル | フェーズ9 論点I で決着済み（再訪条件: 画像がないと伝わらない要望が3件） |
| AI の参加 | フェーズ9 論点K で決着済み。`authorKind` の口は既にある |
| SSE / WebSocket | ポーリングで足りる前提（社内・数十人）は変わっていない |
| スレッド・リアクション・全文検索 | 規模に対して過剰。kintone パリティ方向 |
| チャットから活動を起こす導線 | 論点F の流出リスクへの本対策だが v2。まず言葉の区別で出す |
| 一覧グリッドへの未読列・チャット列 | 論点J。1万件の一覧にチャットの概念を持ち込まない |

## 6. この整理が置いている前提

崩れたら結論ごと見直すもの:

| 前提 | 依存している結論 |
|---|---|
| 社内・数十人・メッセージは1対象あたり多くて数十件 | ポーリング8秒で足りる（論点J）／メッセージ取得が limit 500 で足りる／仮想スクロール不要 |
| 案件チャットに顧客は現れない（社内専用） | 役割の定義（決定B）。顧客とのやりとりを載せるなら認可も添付も別設計 |

### 9-9. 実装中に決めたこと・見つけたもの

**追記1（欠陥）: `POST` に `as_of` を付けると、行は書かれるのに 404 が返る。**
完了条件11 をサーバ側で確かめようとして踏んだ。作成そのものは現在に対して行われて成功するが、
返すために読み直すのが `as_of` 時点（＝その行がまだ無い時点）なので、**書けたのに失敗が返る**。
更新（PATCH）は行レベル認可の手前で弾けていたので今まで見えていなかった。
**フェーズ8 で見つけた「POST だけ守りが1枚少ない」の2例目**で、原因も同じ
— *既存行を前提にした守りは、行がまだ無い操作をすり抜ける*。
対処は入口（`resolveContext`）で `as_of` + 非 GET を 400 にする（`snapshot` と同じ形）。
`app.ts` にあった `isHistorical` の分岐は、そこに来ないので消した。回帰テストつき。

**追記2（決定）: 「書けない理由」は代わりにできることまで出す。**
決定S（フェーズ7）はこれまで「なぜ効かないか」だけだったが、viewers が3ロールに増えて
「営業マネージャーなど」という決め打ちが制作担当への嘘になったので、**自分のロール名**を
定義から引いて出すようにし、ついでに「案件のやりとりには書ける」を足した
（`森 次郎（制作担当）は この業務を読む立場。案件を直せるのは担当者と管理者だけ（案件のやりとりには書ける）`）。

**追記3（決定）: `_permissions` に `create` を足さない。**
案件詳細を開けている時点でその人はフローの参加者で、`appendBy: 'participants'` は
参加者全員に開く。**レコード単位の可否ではない**ので、FE 側の「書けるか」は
`as_of` を見ているかどうかだけで決まる。`_permissions` はレコードごとの操作可否の場所なので置かない。

**追記4（見つけたもの・直した）: `alt diff` の締め行が嘘をついていた。**
「遷移が変わった業務フロー N 本」と出していたが、合併グラフは**そのフローに1件でも差分が
あれば添える**（変わっていない段階も位置の基準に要る）ので、遷移が変わっていないことのほうが多い。
このフェーズの差分（遷移は不変）で表に出たので「図を添えた業務フロー N 本」にした。

**追記5（見つけたもの・直した）: `packages/cli/src/diff.ts` が grep から消えていた。**
`formatDiff` の番兵が `let group = '\0'` だったため、**ファイルが binary 扱いになり
`grep` が何も言わずに飛ばす**（実際に「この関数はどこにも無い」と誤認した）。
番兵を `undefined` にして解消。⚠ 文字列の番兵に NUL を使わない。

**追記6（記録）: ポーリングの `setInterval` は3本目になった**（未読バッジ・要望チャット・案件チャット）。
§8-2 論点20 の「画面が増えるほど効く」の実例が1つ増えた形で、規律（部品に fetch を持ち込まない・
既存パターンを踏襲する）は守っている。

**追記7（完了処理で見つけた）: 決定C が定義の中だけで、画面では確かめられなかった。**
完了条件6 は「制作・**MEO運用**が読み書きできる」なのに、**従業員マスタに MEO運用担当が
1人も居なかった**ので、HTTP で確かめようとして初めて気づいた（`viewers` に足しただけでは、
その立場の人が居るとは限らない）。さらに seed の引き継ぎ会話は、**MEO の受注案件
（`d-yamada-meo`）の引き継ぎ先を制作担当にしていた** — 引き継ぎ先は商材で決まる
（求人広告 → 制作 / MEO → 運用）ので、決定C の理由づけが seed の中で崩れていた。
久保 綾（`meo_operator`）を足し、返信の主を差し替えて解消。
⚠ **ロールを定義に足したら、そのロールの人がマスタに居るかまで見る。**
