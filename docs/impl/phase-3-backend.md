# フェーズ3: バックエンド

ハブ: [../implementation.md](../implementation.md)

**目的**: 定義から REST API を生やし、業務フローに沿ったデータ操作ができるようにする。
**このフェーズが最も重い。**

> **着手時に詳細化すること。** いまは概要と完了条件だけ。

---

## タスク概要

### 3-1. 定義レジストリ

`alt apply` が出した JSON を読んで保持する。テーブル・フロー・バインディングを引ける状態にする。

### 3-2. REST API の自動生成

```
GET    /api/{table}?flow=...&as_of=...
GET    /api/{table}/{id}
POST   /api/{table}
PATCH  /api/{table}/{id}
POST   /api/{table}/{id}/advance     ステップ遷移
```

**バインドされていないテーブルはルートを生やさない。** `product-concept.md` §3-2 の
「バインドされていないテーブルは使えない」を技術的に強制するのがここ。

### 3-3. 有効期間型の書き込み

**避けて通れない部分。** 更新は `UPDATE` ではなく、

1. 現在行の `valid_to` を閉じる
2. 新しい値で INSERT する

をトランザクションで行う。`changed_by` / `changed_flow` / `changed_step`（変更の文脈）も記録する。
読み取り側は `@alt/sql` の SQL 変換が既に対応済み。

### 3-4. 出口条件の評価

一覧で数百件を**まとめて評価する**（レコードごとにコードを実行しない）。
`compilePred` が生成する述語を SELECT 句に埋め込む。`condition-ast.md` §5-1 に形がある。

手動チェック分は `_manual_check` から引く。

### 3-5. ステップ遷移

- `next` に定義された遷移かを検証する
- 出口条件が未充足でも**進める。ただし記録に残す**（`product-concept.md` §4-3）
- 管理者は任意のステップへ移動できる
- `_flow_state` の現在行を閉じて新しい行を作る

### 3-6. 認可と開発用ユーザー詐称

- フロー参加（バインディングの `access` の範囲）+ ステップ操作（ステップの `role`）の2層
- 行レベル: 読みは全員、書きは担当者＋管理者
- レコードごとに `_permissions` をレスポンスに含める（**FEに認可ロジックを複製しない**）
- 認証は実装せず `X-Dev-User` ヘッダで代替。**本番ビルドにコードごと含めない**

---

## 完了条件

- 案件の一覧・詳細が取得でき、各レコードに現在ステップ・出口条件の充足状況・`_permissions` が乗る
- 案件を更新すると有効期間型で新しいバージョンが積まれ、前のバージョンが `as_of` で読める
- ステップを進められ、`_flow_state` に履歴が残る
- 担当者でないユーザーでは更新が拒否される
