## いま作っているもの

alt-kintone は「業務フローを第一級の概念に置いた、AI前提の業務アプリ基盤」
（構想: [product-concept.md](product-concept.md)）。

**ブラウザで動作確認できる最小スコープは達成した**（2026-08-06、フェーズ4完了）。

> **ゴール**: 営業フロー1本が、案件一覧・詳細・出口条件チェックリスト・ステップ遷移として
> ブラウザで動くこと。 → **達成**

最小スコープなので、以下は**意図的に作っていない**。ここから手を広げるときは、
何のために広げるのかを先に決めること。

| 作らないもの | 理由 |
|---|---|
| 求人広告制作フロー / MEO運用フロー | 営業フロー1本で構想は検証できる。※ **2本目はフェーズ9 の要望フローで先に載った**（客先業務ではなく開発の業務） |
| 管理画面FE | バインディングのビューは後でよい |
| `alt plan` | `apply` だけで動く。※ フェーズ10 の `alt diff` は**別物** — plan は「DB に何が起きるか」、diff は「**業務に何が起きるか**」 |
| 定義の版（`_definition_version`）・適用差分の通知・任意2版の比較 | フェーズ10 で不要と分かった。要求を満たすのは**提案差分**（未適用の「こう変える予定」）だけで、それは**版の仕組み無しに作れる** |
| FEの自動生成 | 初回は手で書く。生成の検証は後 |
| 条件式ビルダー（`deal.amount.gt(0)` の型安全な書き味） | **AST を直接書けば動く**。書き味は動くものを見てから |
| 認証 | 決定済み（外部IdPに委譲、プロトタイプでは実装しない） |
| 一覧の範囲選択・コピペ・列リサイズ・列並び替え・保存済みビュー | フェーズ6で明示的に落とした（要求に無い）。「スプレッドシートライク」は操作感の要求であって表計算の再実装ではない |
| 一覧の列選択（`fields=`）・FK先の名前でのソート・未確認件数でのソート | 窓が小さいのでペイロードは問題にならない / 解決機構はあるので必要になってから |

フェーズ1〜4（**ブラウザで動作確認できる最小スコープ**）に加えて、フェーズ5で
**業務フローを営業自身が読める**ようになり（`#/flows/sales`）、フェーズ6・7で
**案件一覧が1万件でもスプレッドシートライクに読み書きできる**ようになった。

フェーズ8 で**営業マネージャーが案件を読めるようになった**（それまでは一覧ごと 403）。
「操作しないが見る」立場はフロー定義の `viewers` に、「同じ段階を複数のロールが操作する」は
`step.roles` になり、§8-2 論点12 が解けた。後者はフェーズ9 の前提だった。

**フェーズ9 で2本目の業務フローが載った。** 開発への改善要望・障害報告そのものを
`request` フローとして定義に書き（**自己適用**）、スクショに赤ペンという運用を
「定義の語彙で対象を指す」形に置き換えた。決定的だったのは
**定義を足しただけで `#/flows/request` の参照画面が増えた**こと（FE を1行も書いていない）
— 「業務フローが第一級」が営業1本の偶然でないことが、ここで示せた。

基盤に足したのは2つだけ（`definitionRef` と `fill: 'createdAt'`）。
一方で**「フローが1本しかない」ことに寄りかかっていた箇所が4つ**露出した
（未読の数え直し / 画面をまたぐエラー / マスタの引き先 / `roles: ROLE_KEYS` の型）。

**フェーズ10 で、要望への返事が「直しました」の一文でなくなった。**
`alt diff` が「適用済みの定義」と「作業ツリーの定義」を比べ、**業務の言葉で**出す
（「出る条件が増えます: 「競合先を確認した」（自動判定）」）。遷移の変更は
**前後を重ねた合併グラフ1枚**で読め、**残るステップは動かない**。さらに
「この条件を足すと、**いま提案にいる 2000 件が全部未充足になります**」まで適用前に出る
— kintone に原理的に出せない情報で、`alt plan`（DB に何が起きるか）に対する**業務側の対**。

⚠ **提案差分は保存物**（適用したら再計算しても何も出ない）なので、**ラベルは計算時に解決して持つ**。
そのおかげで、見送りで定義から消えたものを指していても当時の言葉のまま読める。

**フェーズ10 で「業務に何が起きるか」が適用前に数字で出るようになった。**
`alt diff` が適用済みの定義と作業ツリーを比べ、**業務の言葉で**「出る条件が1つ増えます」と出す。
`--request <id>` を付ければ要望に「変更案」として添えられ、**起票者が自分の要望でこう変わるを
読める**。§8-2 論点5（定義差分の出し方）はここで解けた — 版を積む仕組みは要らなかった。

**営業フロー1本がブラウザで動き、フローそのものも読め、一覧が1万件でも実用になった**。
案件の一覧・詳細に現在ステップと出口条件のチェックリストが出て、**データを直すと自動判定が
勝手に充足に変わり**、未充足の条件には「どうすれば充足するか」が出る。未充足でも進めるが
記録に残り、`as_of` で過去が読め、担当者でなければ編集ボタンが出ない。**異動してきた営業は
`#/flows/sales` で、ゴール・段階の意図・遷移・使うデータを定義ファイルなしで把握できる**。

一覧は**1万件を上下スクロールで全件辿れる**（窓1枚 12ms）。ステップ・担当（「自分の案件」）・
商材・確度・状態・見込み月・案件名で絞れ、列見出しで並べ替えられる。**絞り込みは URL に載るので
そのまま共有できる**。取得の合間に誰かが更新しても行はズレない（`snapshot` で時点を固定する）。
**セルは Enter で編集できる**（フェーズ7）。確定はセル単位の `PATCH` で版として残り、
金額を直すと未確認件数がその場で動く。編集に入れないセルでは理由が言葉で出る。

**改善要望が業務フローとして回る**（フェーズ9）。どの画面からでもヘッダの「困りごとを出す」で
1クリック起票でき、**必須は種類と困りごとの2つだけ**。画面・業務フロー・ステップ・対象データ・
起票時刻は**アプリが機械で添える**。対象は定義の語彙（`definitionRef`）で指し、画面には
「営業（新規開拓） ＞ 提案 ＞ 導入時期を確認した」と業務の言葉で出る。要望自身も
起票 → 受付 → 対応中 → 適用済 → 完了 のフローに乗り、**やりとりを1件書くと出口条件
「起票者に返信した」が自動で充足に変わる**。返信は未読としてナビに出る。
**制作担当（営業フローには参加していない）も起票でき、自分の要望を進められる**。

**要望への返事に「こう変わります」が付く**（フェーズ10）。開発側が定義を直したら
`alt diff --request <id>` で変更案を要望に添えると、起票者の画面に
「＋ 出る条件が増えます: 「競合先を確認した」（自動判定）／案件の「競合先」に相手の社名を
入れると充足する」と業務の言葉で出る。遷移の変更は**前後を重ねた1枚**で読め、
**「いま提案にいる 2000 件が全部未充足になります」**まで適用前に出る。
新しい項目を見ている条件は数えられないので、**その理由も業務の言葉で**出る。
添えた変更案は**適用後も、見送って定義から消したあとも、当時の言葉のまま残る**。

開発は Docker 内で行う。

```sh
docker compose up -d
docker compose exec dev pnpm verify              # check:wiring → fmt:check → typecheck → lint → test

docker compose exec dev pnpm alt validate        # 定義の検証（--json あり）
docker compose exec dev pnpm alt apply --recreate            # SQLite にスキーマを作り直す
docker compose exec dev pnpm alt export --out data/definitions.json  # サーバーが読む形で書き出す
docker compose exec dev pnpm alt seed --reset    # デモデータ

docker compose exec -d dev pnpm dev              # FE （ホストからは localhost:5273）

curl -H 'X-Dev-User: yamada@example.com' 'localhost:3100/api/deal?flow=sales'
```

## 実装中ずっと効く決定

詳細は [product-concept.md §8-1](product-concept.md)。ここには**実装のたびに参照するもの**だけ置く。

1. **定義は TypeScript DSL**。`alt apply` 時に JSON へ変換してバックエンドに渡す。Go はJSONを読むだけ
2. **API は REST 自動生成**。`/api/{table}`。`_permissions` は各レコードに含める。**グリッドの取得も REST 拡張**（2026-08-08 旧論点16決着。GraphQL 併用は再訪条件つき見送り — §8-1）
   - **時点のパラメータは2つあり、意味が違う**（フェーズ6 決定A）。`as_of` = 過去を見る（**読み取り専用**。`_permissions.update` が落ちる）／ `snapshot` = いまを固定して読む（**読み取り専用にしない**。窓取得の行ズレ対策。GET 専用）。1つにまとめると一覧の全行が編集不可になる
   - 一覧のフィルタは**フィールド毎のパラメータ**（`status=open` / `title_like=看板` / `expectedCloseMonth_gte=2026-08` / `step=proposed`）。**サーバ内部で条件式 AST に変換する**ので、FE は AST を組み立てない
3. **バインドされていないテーブルは API が生えない**。これを技術的に強制するのがバックエンドの役割
4. **全テーブルに有効期間型（SCD Type 2）の列を自動付与**する。定義には書かない。更新は「前の行を閉じて INSERT」。**外部キーの索引も DDL が自動で付ける**（フェーズ6 決定G。定義に書かせない）
5. **現在ステップは `_flow_state` テーブル**（レコード × フローの関係として持つ。有効期間型）。業務テーブルの列にはしない
6. **手動チェックは `_manual_check` テーブル**。出口条件は**明示キー**で識別する（ラベルをキーにしない）
7. **認可は業務フロー定義から導出**する。権限設定を別に書かない。行レベルは「読みは全員、書きは担当者＋管理者」
   - **参加の種類は4つ**（フェーズ8）: `admin` / `operator`（どれかのステップの `roles` に居る）/ `viewer`（`flow.viewers` に居る。**読み取り専用**）/ `none`（403）。入口で1回決めて `RequestContext` に載せる
   - **ステップの担当は `roles: string[]`**（複数可）。「全員が操作する」は `ROLE_KEYS` の導出で書く（列挙しない）
8. **認証は実装しない**。`X-Dev-User` ヘッダでユーザーを詐称する。**本番ビルドにコードごと含めない**
9. **条件式は SQL に変換できる範囲**に限る（レベル3: 集計・比較まで）。任意コードは書けない
10. **AST は完全に明示的**。暗黙結合などの糖衣は TS 側で展開してから AST にする
11. **定義そのものを指すフィールドは `definitionRef`**（フェーズ9）。`reference()` が
    外部キーを新しい型ではなく `references` で表しているのと同じ形で、`type` は `text` のまま。
    値は合成キー（`sales.proposed.timing_confirmed`）。**解決は `@alt/dsl` の純関数をサーバとFEが共有する**
    — 「保存できたのに画面に出ない」を構造的に起こさないため
12. **サーバが埋める値は `fill: 'createdAt'` の1つだけ**（フェーズ9）。一般的なデフォルト値の
    機構にしない（式を持ち込むと「定義はただの JSON」が崩れる）。
    ⚠ **`_version.validFrom` を作成時刻に使わない** — 更新のたびに動く
13. **シェルが共通化するのは `_flow` を描くところまで**（フェーズ9 決定H）。
    現在地・出口条件チェックリスト・遷移ボタンは `shell/flow/` に1つだけ置く。
    **一覧とフォームは各業務フローの手書きのまま**（ここを共通部品にすると kintone の失敗構造）
14. **API クライアントは業務フローごとに1本**（フェーズ9）。呼び出しごとに `flow` を渡せる
    ようにしない — 指定漏れが認可の範囲の取り違えになる
15. **定義に対する純関数は `@alt/dsl`**（フェーズ10 で `layoutFlow` を FE から移設）。
    Go に移植しないもの（`referencedFields` / `layoutFlow`）も**契約外と注記して同じ棚に置く**。
    CLI・サーバ・FE のどこからでも同じ関数を呼べることのほうが、棚の純度より効く
16. **保存する計算結果は、業務の言葉を解決してから保存する**（フェーズ10）。
    提案差分（`change_request.proposal`）が例。機械キーだけ保存すると、そのあと定義が
    変わったり消えたりしたときに**何も表示できなくなる**。
    ⚠ `definitionRef`（機械キー保存・表示時解決）とは**時制が逆**なので、混同しない
    — あちらは「いまの定義のどこを指すか」、こちらは「そのとき定義がどうだったか」
