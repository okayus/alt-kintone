## 1. この設計を読むのに要る前提

実装の説明に入る前に、判断の材料になる概念を並べる。
この節の語は以降でそのまま使う。

### 1-1. 画面の状態をどこに置くか

「いま何で絞り込んでいるか」は、置き場所が三つある。

- **コンポーネント状態**：React の `useState` に持つ。書きやすいが、リロードで消え、URL を共有しても相手には伝わらない。
- **URL**：クエリ文字列に持つ。リロードしても残り、URL を渡せば相手の画面が同じ状態になる。ブラウザの戻るでも復元される。
- **サーバ**：ユーザーごとの保存済みビューとして持つ。kintone の「一覧」がこれにあたる。作る手間が増え、共有には別の仕組みが要る。

案件一覧のフィルタは URL に置いてある。
決め手は共有である。
「この条件の一覧を見てほしい」を Slack に貼れることが、絞り込み機能の価値の半分を占める。
コンポーネント状態に置くと、この価値がまるごと失われる。

### 1-2. 誰が絞り込むか

絞り込みの実行場所も二つある。

- **クライアント側**：全件をブラウザに取ってから JavaScript で絞る。実装は単純で、応答も速い。
- **サーバ側**：条件をリクエストに載せ、SQL の `WHERE` で絞る。

案件が1万件ある前提では、前者を選べない。
1万件のレコードを毎回送ると初回表示が待てる時間に収まらず、そもそも一覧は仮想スクロールで
「見えている100件ずつ」しか取らない設計になっている（[phase-6-list-grid.md](../impl/phase-6-list-grid.md) §2-1）。
手元に全件がないのだから、手元では絞れない。

サーバ側で絞ると決めた瞬間に、次の問いが立つ。

### 1-3. 絞り込みの語彙は誰が決めるか

クライアントがサーバに条件を伝える方法には幅がある。
両極を書くと、こうなる。

- **条件式そのものを送る**：AND や OR やネストを含む式を JSON なり文字列なりで組み立てて送る。表現力は最大になる。
- **フィールドごとのパラメータを送る**：`status=open` のような決まった形だけを受ける。表現力は落ちるが、URL が人間に読める。

この系は後者を採っている。
理由は三つあって、いずれも [list-query.ts](../../packages/server/src/list-query.ts) の冒頭コメントに書かれている。
条件式を URL に載せると読めなくなること、共有した URL を手で直したときに壊しやすいこと、
そしてサーバ側の検証面積が「フィールドの型の数」ではなく「式のノードの種類の数」に膨らむことである。

ただし、表現力を落とした分をどこかで取り戻す必要はない。
サーバの中では、受け取ったパラメータを条件式に組み直しているからである（第4節）。

### 1-4. 入力をいつ確定とみなすか

テキスト入力には、値が変わるたびに反応する形と、確定操作を待つ形がある。
検索欄で前者を選ぶと、「看板」と打つ途中の「か」「かん」でも通信が飛ぶ。
一覧のフィルタでは、これに加えて URL にも打ちかけの文字列が載る。

この違いは、状態を URL に置いたことで初めて問題になる。
コンポーネント状態なら打ちかけの値が誰の目にも触れないが、
URL は共有される前提の場所なので、`title_like=看` が意図した条件なのか打ちかけなのか、
受け取った側には区別が付かない。

### 1-5. 非同期の取得が複数飛ぶときに起きること

一覧は窓（100件ずつ）を並行して取りに行く。
そのため、絞り込みを変えた直後には、古い条件で投げたリクエストがまだ空中にある。
何もしなければ、古いレスポンスが新しいレスポンスより後に届いて画面を上書きすることがある。

この対策が「世代」である。
取得を投げるときに現在の世代番号を控え、返ってきたときに世代が変わっていれば捨てる。
実装では `token` という参照がその番号を持つ（[useDealPage.ts](../../apps/main/src/flows/sales/useDealPage.ts)）。

## 2. 全体の流れ

フィルタは四つの層を通る。
層と層のあいだに変換表がないことが、この設計の主眼である。

```
URL              ?status=open&title_like=看板
  ↓  nuqs        apps/main/src/flows/sales/dealQuery.ts
FE の状態         { status: ['open'], title_like: '看板' }
  ↓  buildQuery  apps/main/src/shell/api.ts
HTTP クエリ       GET /api/deal?flow=sales&status=open&title_like=看板
  ↓  parse       packages/server/src/list-query.ts
条件式 AST        and(in(status, ['open']), contains(title, '看板'))
  ↓  compilePred packages/sql/src/compile.ts
SQL              WHERE r.status IN (?) AND r.title LIKE ? ESCAPE '!'
```

（SQL は要点だけを書いた。実際には識別子が引用符で囲まれ、有効期間の条件が先頭に付く。`r` はルートテーブルの別名である）

パラメータ名は URL から HTTP まで同じ文字列である。
`status` は FE でも `status`、API でも `status`、そして定義のフィールド名としても `status` である。
名前が変わる箇所がないので、対応表を読まなくても、URL を見れば何で絞られているかがわかる。

条件式になるのはサーバに入ってからで、FE は条件式を組み立てない。
条件式の解釈がサーバの1箇所に閉じ、FE とサーバで解釈がずれる余地がなくなる。

## 3. フロントエンドの実装

### 3-1. URL がフィルタ状態の置き場（dealQuery.ts）

[dealQuery.ts](../../apps/main/src/flows/sales/dealQuery.ts) の `dealQueryParsers` が、
この画面で使えるフィルタの全語彙である。

```ts
export const dealQueryParsers = {
  step: parseAsArrayOf(parseAsString, ','),
  ownerEmployeeId: parseAsArrayOf(parseAsString, ','),
  productType: parseAsArrayOf(parseAsString, ','),
  dealType: parseAsArrayOf(parseAsString, ','),
  confidence: parseAsArrayOf(parseAsString, ','),
  status: parseAsArrayOf(parseAsString, ','),
  expectedCloseMonth_gte: parseAsString,
  expectedCloseMonth_lte: parseAsString,
  title_like: parseAsString,
  sort: parseAsString,
}
```

キーの命名がサーバの語彙にそのまま従っている。
接尾辞のない名前は候補の列挙、`_gte` と `_lte` は範囲、`_like` は部分一致を表す（第4節）。

`useDealQuery()` がこの宣言から三つの値を作る。

- `filters`：API に渡す `Record<string, string>`。配列はカンマで繋ぎ、`null` のキーは落とす。
- `sort`：並び順。絞り込みではないので `filters` から分けてある。
- `unknownKeys`：URL にあるが解釈できなかったキー（3-3 で扱う）。

置き場は `location.search` である。
この画面のルータはハッシュ（`#/flows/sales`）を使っているので、二つは干渉しない。
nuqs が `?...` だけを書き換え、ハッシュには触らない（[main.tsx](../../apps/main/src/main.tsx) のコメント）。
その副産物として、一覧から詳細へ移動して戻ってもフィルタが残る。

### 3-2. フィルタ面は手書きで、語彙は定義から取る（DealFilters.tsx）

[DealFilters.tsx](../../apps/main/src/flows/sales/DealFilters.tsx) は、
汎用のフィルタビルダーではなく、営業の案件一覧のためのフィルタ面として手で書いてある。
フォームを定義から自動生成しないのと同じ判断で、業務画面を共通部品に寄せると
部品の表現力が画面の上限になる、という理由による（[product-concept.md](../product-concept.md) §4-3）。

手書きではあるが、選択肢とラベルと型は定義から引いている。

| 出どころ | 面に出るもの |
|---|---|
| `sales.steps`（フロー定義） | ステップのトグル。ステップを足すとフィルタも増える |
| `dealDef.fields.status?.values` 他（テーブル定義） | enum の選択肢。`{key, label}` をそのまま使う |
| `masters.employees` | 担当。先頭に `me`（「自分の案件」）を挿す |

文言を画面側に書き写さないので、定義のラベルを直せば面の表示も変わる。
逆に、面に出す項目の取捨（v1 は7項目）だけが画面側の判断として残っている。

検索欄だけは挙動が違い、入力のたびには反映しない。
Enter を押すか、入力欄から離れたときに確定する（1-4 の理由）。

### 3-3. 綴り間違いを黙って捨てない

nuqs は宣言したキーしか読まない。
`?statuss=open` と書かれていても、`statuss` は誰の目にも触れずに消える。
すると「絞り込んだつもりで絞られていない一覧」がそのまま表示され、
共有した相手はそれを絞り込み済みの一覧だと思って読む。

そこで `useDealQuery()` は `location.search` を直接読み、
宣言済みのキーと `as_of` のどちらにも当たらないものを `unknownKeys` として返す。
`DealFilters` はこれを警告として画面に出す。

```
URL の statuss は絞り込みとして解釈できないので無視した。
使えるのは step, ownerEmployeeId, productType, ...
```

ここで押さえておきたいのは、未知のキーが FE から先へ進まないことである。
`filters` は nuqs の状態から組み立てられるので、宣言にないキーはサーバに送られない。
サーバも未知のパラメータを 400 で弾くが（第4節）、その経路には届かない。
つまり、面に出ていないフィールドで絞りたい場合、URL に手で書いても効かない。
`dealQueryParsers` に宣言を足すか、API を直接叩くかのどちらかになる。
`dealType` は宣言があって面に無いので、URL に書けば効く数少ない例である。

### 3-4. フィルタが変わったときの再取得（useDealPage.ts）

[useDealPage.ts](../../apps/main/src/flows/sales/useDealPage.ts) は、
絞り込み、並び、時点、詐称中のユーザーを一つの文字列に畳んで世代の鍵にする。

```ts
const key = JSON.stringify([filters, sort ?? '', asOf ?? '', user])
```

オブジェクトや関数は毎レンダーで同一性が変わるため、React の依存配列に直接置くと「変わっていないのに変わったと判定される」。
文字列に畳んでから比べているのは、この判定を値の中身で行うためである。

この鍵が変わると、取得済みの行をすべて捨てて先頭から取り直す。
これを**ハード世代**と呼んでいる。
スクロール位置も先頭に戻る。
絞り込みを変えれば5,000行目という位置の意味が消えるので、位置を保つほうが不自然になる。

対になるのが**ソフト世代**で、セル編集の確定後に走る。
行もスクロールも保ったまま、読み取り時点と総件数だけ取り直す。
こちらでハード世代を使うと、1セル直すたびに一覧が白くなって先頭へ飛び、
「下のセルへ移って次を直す」という操作が成立しない（[phase-7-list-grid-edit.md](../impl/phase-7-list-grid-edit.md) 決定K）。

## 4. サーバの実装

### 4-1. パラメータから条件式へ（list-query.ts）

サーバは、予約済みのキー以外をすべてフィルタとして解釈する。

```ts
export const RESERVED_QUERY_KEYS = ['flow', 'as_of', 'snapshot', 'limit', 'offset', 'sort', 'step']
```

残りは接尾辞で演算子が決まる。

| パラメータの形 | 条件式のノード | 生成される SQL |
|---|---|---|
| `status=open,won` | `in` | `IN (?, ?)` |
| `expectedCloseMonth_gte=2026-07` | `compare` (gte) | `>= ?` |
| `title_like=看板` | `contains` | `LIKE ? ESCAPE '!'` |

複数のパラメータは `and` で束ねる。
OR はパラメータ間では書けず、同じフィールドの候補列挙（カンマ区切り）としてだけ表現できる。
1-3 で落とした表現力がここに現れている。

処理の前にキーをソートしているのは、SQL に積むパラメータの順序が
リクエストのキー順に依存しないようにするためである。
順序が安定していれば、テストで SQL とパラメータ列をそのまま比較できる。

### 4-2. 値の検証はフィールドの型で決まる

`coerce()` が、文字列をフィールドの型に合う値へ変換する。
変換できなければ 400 を返す。

```
expectedCloseMonth（見込み受注月・yearMonth）の値として読めない: 2026/07
→ YYYY-MM で渡す
```

型と演算子の組み合わせも見る。
`_like` は text にしか付けられず、`_gte` と `_lte` は順序のある型（integer、date、datetime、yearMonth）にしか付けられない。

エラーに直し方を添える形は `alt validate` と揃えてある。
定義を書くのが AI であるのと同じく、URL を組み立てるのも AI である場合があり、
読んで自分で直せることが前提になっている。

### 4-3. `me` は展開せずに残す

担当の絞り込みで `ownerEmployeeId=me` と書ける。
このとき、サーバはログインユーザーの id に置き換えず、
「現在のユーザー」を指すノードのまま条件式に載せる。

置き換えないのは、URL が共有されるからである。
展開してしまうと、共有された URL は「送った人の案件」を指す。
展開しなければ、受け取った人にとっての「自分の案件」になる。
「自分の案件」という語の意味に合うのは後者である。

### 4-4. ステップだけ扱いが違う

現在ステップは業務テーブルの列ではない。
レコードとフローの関係として `_flow_state` テーブルに持っている
（業務テーブルに `step` 列を持たせると、kintone と同じ構造になる）。

そのため `step` はフィールドのフィルタとして扱えず、専用の分岐になっている。
対象のテーブルがそのフローの `target` でなければ、ステップで絞ることも並べることもできず、
その旨を 400 で返す。

### 4-5. 条件式から SQL へ（query.ts）

[query.ts](../../packages/sql/src/query.ts) の `fromAndWhere()` が
`FROM` と `WHERE` を組み立てる。
フィルタの条件式は `compilePred()` に渡され、出口条件（フローを次に進めてよいかの判定）と
同じコンパイラを通る。

同じコンパイラを通すことに実利がある。
フィルタの表現力が条件式の部分集合になる代わりに、
SQL 変換と方言差の吸収と適合テストが、フィルタのために書き直さずに済む。
フィルタ専用の SQL 生成を持たないことが、[phase-6-list-grid.md](../impl/phase-6-list-grid.md) 論点C の要点である。

部分一致は `LIKE` になるが、ユーザーが打った `%` はワイルドカードにならない。
`likePattern()` が `%` と `_` と `!` をエスケープしてからパターンを組む
（[compile.ts](../../packages/sql/src/compile.ts)）。
「部分一致であってパターンではない」という決定（決定B）を、ここで守っている。

もう一つ、総件数と一覧が同じ `fromAndWhere()` を通ることが効いている。
総件数は仮想スクロールのスクロールバーの長さを決める値なので、
一覧と違う条件で数えられると、行数と総数が食い違ってスクロールが破綻する。
関数を共有することで、条件がずれない状態を構造として保っている。

## 5. nuqs について

[nuqs](https://nuqs.dev/) は、URL のクエリ文字列を React の状態として読み書きするライブラリである。
バージョンは 2.9.5（`apps/main/package.json`）。
`useState` と同じ書き心地で、値の置き場が URL になる、と考えるとよい。

### 5-1. 使っている API

- **`NuqsAdapter`**：ルータとの繋ぎ込み。`main.tsx` でアプリ全体を包む。ここでは `nuqs/adapters/react`（素の React 用）を使っている。
- **`useQueryState(key, parser)`**：キー1つを読み書きする。`App.tsx` の `as_of`（時点指定）がこれ。
- **`useQueryStates(parsers, options)`**：キーを複数まとめて読み書きする。`[values, setValues]` を返し、`setValues` は部分更新を受ける。案件一覧のフィルタはこちら。
- **`parseAsString`**：文字列としてそのまま読む。
- **`parseAsArrayOf(itemParser, separator)`**：区切り文字で分割して配列にする。区切りの既定はカンマだが、コードでは `','` を明示している。

パーサは「URL の文字列から値への変換」と「値から文字列への変換」の組である。
`parseAsInteger` や `parseAsIsoDate` のような型付きのものもあるが、
この画面では文字列のままサーバへ渡してサーバに検証させているので、使っていない。

### 5-2. 値を消す方法

`null` を書くとキーが URL から消える。
これは nuqs の約束で、`clear()` はこれを全キーに対して行う。

```ts
clear: () => {
  void set(Object.fromEntries(Object.keys(dealQueryParsers).map((key) => [key, null])))
}
```

`Toggles` が選択ゼロのときに `null` を渡しているのも同じ理由である。
空配列を書くと `status=` という空のパラメータが URL に残る。

### 5-3. 知っておくとよいオプション

`useQueryStates` の第2引数に渡せる。
コードで指定しているのは `history` だけである。

- **`history`**：`'replace'`（既定）か `'push'`。`push` にすると更新のたびにブラウザの履歴が1段増える。フィルタのトグル1回ごとに戻るが1段増えると、一覧から詳細へ行って戻るのが面倒になるため `replace` を使う。既定と同じ値だが、意図を残すために明示してある。
- **`clearOnDefault`**：既定 `true`。既定値と同じ値を書いたときキーを URL から落とす。URL を短く保つための挙動である。
- **`limitUrlUpdates`**（旧 `throttleMs`）：URL の更新頻度の上限。既定は 50ms。ブラウザの History API にレート制限があるための配慮で、Safari では 120ms 程度が要るとドキュメントにある。
- **`shallow`**：サーバコンポーネントを持つフレームワーク向けのオプション。この構成（Vite と素の React）では関係しない。
- **`scroll`**：更新後にページ先頭へスクロールするか。既定 `false`。

### 5-4. 踏みやすい二つの穴

一つは、宣言していないキーが存在しないものとして扱われることである。
3-3 の `unknownKeys` はこれへの対処で、nuqs の機能ではなく手で書いた部分である。

もう一つは、nuqs の更新が `popstate` イベントを出さないことである。
`pushState` と `replaceState` はイベントを発火しないという仕様なので、
`window.addEventListener('popstate', ...)` で URL の変化を追いかけても、
nuqs 自身が起こした変化には追随できない。
`useSearch()` が購読ではなくレンダー時に `location.search` を読む形になっているのは、
nuqs の状態が変わればどのみち再レンダーが起き、そのときに読み直せば足りるからである。

## 6. 判断のまとめ

| 採った形 | 採らなかった案 | 理由 |
|---|---|---|
| フィルタ状態を URL に置く | コンポーネント状態 | 絞り込んだ一覧をそのまま共有できる。戻る操作とリロードでも消えない |
| URL のキー名を API のパラメータ名と同じにする | 画面用の名前を付けて変換する | 変換表がないので、URL を読めば何で絞られているかがわかる |
| フィールドごとのパラメータ | 条件式そのものを URL に載せる | 人が読める。壊れにくい。検証面積が型の数で収まる |
| 条件式への変換はサーバ | FE で条件式を組み立てる | 条件式の解釈が1箇所に閉じ、FE とサーバでずれない |
| 出口条件と同じコンパイラを通す | フィルタ専用の SQL 生成 | SQL 変換と方言差と適合テストを作り直さずに済む |
| `me` を展開せずに残す | ログインユーザーの id に置換 | 共有した URL が、受け取った人にとっての「自分の案件」になる |
| フィルタ面は手書き | 定義から自動生成 | 業務画面を共通部品に寄せると、部品の表現力が画面の上限になる |
| 未知のキーを画面に出す | 黙って無視 | 絞られていない一覧を絞り込み済みだと思って共有する事故を防ぐ |

## 7. いま弱いところ

読むときに気付いた点を、直し方を決めずに置いておく。

`RESERVED_QUERY_KEYS`（`list-query.ts`）は、`context.ts` が読むパラメータと同じ集合でなければならない。
片方だけ増やすと、増やしたほうが未知のパラメータとして 400 になるか、黙って無視されるかのどちらかになる。
コード側にも警告のコメントがあるが、機械的な検査はない。

フィルタ面に出す項目は手で選んでいるので、テーブル定義にフィールドを足しても面には現れない。
`dealQueryParsers` に足せば URL では効くようになり、面に出すにはさらに `DealFilters` を触ることになる。
定義とフィルタ面のあいだに、ラベルは自動で追随するが項目は追随しない、という段差がある。

一覧の性能は、条件式が何を読むかで決まる（[product-concept.md](../product-concept.md) §8-2 論点17）。
現在の実装は全ステップの出口条件を毎行評価しているので、
ステップと条件が増えるとフィルタの速さにも効いてくる。
